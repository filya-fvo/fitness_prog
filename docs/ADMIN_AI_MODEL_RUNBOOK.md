# Локальный ИИ и распознавание этикеток на VPS

Production не обращается к Groq, OpenAI или другому внешнему AI API. На VPS
работают два закрытых Docker-сервиса:

- `llm`: `llama.cpp` и `Qwen3-4B-Instruct-2507 Q4_K_S` для русских текстовых ответов
  ИИ-тренера, без генерации скрытых рассуждений;
- `ocr`: PP-OCRv5 mobile и Cyrillic mobile через RapidOCR 3.9.2 /
  ONNX Runtime 1.24.4 для чтения фото пищевой этикетки. Tesseract `rus+eng`
  остаётся в образе для явного отката.

Фото попадает во внутренний PP-OCRv5, а распознанный текст разбирает
детерминированный OCR-парсер. Фото и текст этикетки не передаются в Qwen:
черновик КБЖУ не зависит от очереди ИИ-тренера и остаётся редактируемым.
Qwen запущен только для текста, без `mmproj`. Порты `8080` и `8090`
не публикуются на VPS и доступны лишь
API в Docker-сети `ai_internal`. Код дополнительно отклоняет любой LLM URL,
который не указывает на `llm` или loopback.

## Ресурсы и ограничения

Основной выпуск `86c49b3` работает на текущем VPS 2 vCPU / 4 ГБ RAM;
проверка опубликованного кода пройдена:

- Qwen ограничен `2800m` RAM (2,734 GiB), `3072m` суммарной памяти RAM + swap,
  2 CPU, контекстом 2048 токенов и одним запросом;
- используются два потока генерации и два потока обработки prompt,
  `batch-size=256`, `ubatch-size=64`; RAM-кэш prompt и context checkpoints
  отключены (`cache-ram=0`, `ctx-checkpoints=0`);
- reasoning отключён на сервере; запрос приложения также передаёт
  `chat_template_kwargs={"enable_thinking":false}`;
- OCR ограничен 512 МБ RAM, 1 CPU и также обрабатывает одно фото за раз;
- бюджет в env по умолчанию — 256 выходных токенов; компактный профиль 4B
  использует 192 токена и общий лимит ожидания 75 секунд, из них очередь ждёт
  не более 5 секунд, затем приложение возвращает безопасный ответ по правилам;
- если модель недоступна, AI-тренер даёт безопасный rule-based ответ, а
  этикетка всё равно может вернуть данные детерминированного OCR-парсера.

Вопросы о боли, времени отдыха между подходами и еде после тренировки не
передаются модели: приложение отвечает проверенными детерминированными правилами.
Вывод модели также отклоняется, если он повторяет сводку приложения вместо
ответа или содержит фрагменты на другом языке.
Дополнительное правило общего подбора рабочего веса на русском/английском
выпущено в `87953e8`: запланированные повторы, устойчивая техника,
запас 2–3 повтора и уменьшение веса при утрате контроля, один уточняющий вопрос.
Ответ имеет источник `rule` и не вызывает модель; живые RU/EN-вопросы
проверены за 0,10 / 0,02 секунды. Анализ истории остался модельным: повтор
предыдущей тренировки вернул `local` за 53,19 секунды. Исправление `a50d2fe`
ставит английскую жалобу на боль выше подбора веса; `pain-free` и `no pain`
не вызывают ложное предупреждение. Локальные проверки и независимый обзор
пройдены; выпуск проверен на VPS: EN-боль — rule за 0,08 с, RU-боль — rule за 0,01 с, pain-free — обычный подбор за 0,02 с. Повтор анализа — local за 47,53 с; API/сайт доступны, OOM и перезапусков нет.

Компактный профиль 4B ограничивает prompt в символах: контекст приложения —
600, каталог — 350, история — 250, вопрос — 700. Профиль и ограничения здоровья
сохраняют приоритет перед историей. Для отдельного анализа профиль ограничен
400 символами, проверенные агрегаты — 800, исходный вопрос — 700. Исторический
разбор тренировок использует отдельные проверяемые facts. Лимит сервера —
2048 токенов вместе с ответом; символы не равны токенам, поэтому максимальный
prompt необходимо проверять токенизатором именно установленной модели.
Для окончательной компактной инструкции (544 знака) насыщенные синтетические
запросы измерены: чат 872 входных токена, отдельный анализ 823. Вместе с
резервом 192 оба проверенных запроса помещаются в контекст 2048; это не
доказательство размера любого возможного текста в токенах.

Исторические тренировочные вопросы (`workout_progress`) формируют проверенные
факты прямо из БД, затем Qwen интерпретирует эти факты без истории ответов модели.
В модель передаются проверенные направления изменений, число занятий и
ограничения сравнения, без абсолютных тоннажа, RPE, длительности и числовых
средних. Полная числовая сводка сохраняется отдельно. Ответ — обычные пункты
«Вывод», «Оговорка», «Следующий шаг»: один вызов, temperature `0`, максимум
256 выходных токенов, timeout 75 секунд и очередь 5 секунд. При успехе
модельные выводы идут первыми, затем четыре короткие строки фактов,
источник `local`. Если только следующий шаг содержит числовое назначение,
его заменяют проверенным серверным действием, сохраняя модельные выводы
и `local`. Неверные наблюдения, неизвестные/Unicode-числа, медицинские
утверждения во всём исходном ответе, обрыв или отказ модели ведут к явному
резервному ответу со сводкой `source=data`. Эти проверки не доказывают
правильность каждого смыслового вывода.
Общий сборщик используется `/ai/chat` и `/ai/analyze`. Последняя тренировка
выбирается по завершённым записям до локального «сегодня», без ограничения
14 дней; периодический разбор применяет обе границы. Недельный запрос включает
нагрузку и восстановление, отмечая отдельные пропуски. План следующего дня
не участвует в разборе завершённых тренировок.

Сервер классифицирует остальные запросы по доменам `workout_progress`, `strength`,
`measurements`, `weight`, `nutrition`, `recovery`, `safety`, `general`. Для
аналитического домена, кроме тренировочного разбора, в Qwen передаются ограниченные агрегаты выбранного
периода. «Месяц» означает 30 дней; явный период ограничен 1–365 днями. Если в
домене нет фактов, модель не вызывается: пользователь получает один уточняющий
вопрос. Тоннаж считается единым backend-правилом: `per_hand × 2`, `total × 1`,
а повторы без веса и интервалы по времени остаются отдельными метриками.

Qwen3-1.7B не прошёл проверку интерпретации реальных тренировочных фактов:
путал рост повторов со снижением и выдумывал причины. Все три итоговых
read-only ответа 4B до выпуска приняты по содержанию: предыдущая тренировка
38,09 секунды, месяц 29,84, неделя 39,73; источник `local`, числовые назначения
следующего шага месяца/недели заменены проверенными действиями. Общий русский
вопрос занял 44,19 секунды, английский вопрос получил русский ответ за 20,22.
Ранние холодные запросы занимали около 45–55 секунд; анализ наблюдался
обычно в пределах 30–50 секунд. После выпуска три анализа вернули `local` за
57,78 / 29,15 / 37,42 секунды; первый одновременно с OCR за 6,77 секунды.
Английский вопрос о питании получил локальный ответ за 14,47 секунды.
Контейнер занимал 1,984–2,56 GiB при лимите 2,734 GiB; OOM и перезапусков нет.
Доступно 609 MiB RAM хоста, swap 1057 MiB против 1049 MiB до выпуска.
Последний локальный прогон: 837 backend-тестов, 49 целевых проверок и Ruff, импорт приложения
проверен. На момент публикации исправления результат повторного GitHub CI ожидается. Наблюдения не гарантируют будущие
качество/время и устойчивость при нагрузке.
Старый GGUF 1.7B после итоговой проверки удалён; для отката требуется загрузка.
Ранний кандидат Qwen3.5-2B также был отклонён из-за ошибок каталога.

На шести реальных фото новый OCR точно прочитал 15 из 21 проверяемого значения;
пик процесса точного OCR-модуля был 342,5 MiB при лимите контейнера 512 MiB.
После живых HTTP-проверок контейнер занимал 286,5 MiB. На молоке
остались пропуски белка и жира, фото курицы не читалось; у десерта энергия
449,1 ккал рассчитана из прочитанных кДж. Числа из состава не подставлялись
в КБЖУ. Это ограниченный проверочный набор, а не обещание полной точности.

Размер GGUF не равен рабочему потреблению памяти. Проверьте тариф, если
доступная память устойчиво ниже 500 МБ, swap постоянно растёт или AI регулярно
не укладывается в timeout.

## Первая установка модели

Модель не хранится в Git. Интернет нужен один раз для загрузки закреплённой
GGUF-конвертации модели Qwen, после этого inference полностью локален.

```bash
cd /opt/fitness/source
sudo sh scripts/install-local-ai-model.sh /opt/fitness/models
sha256sum /opt/fitness/models/qwen3-4b-instruct-2507-q4_k_s.gguf
```

Ожидаемая SHA-256:

```text
952af947c6aabf7b72f7d8e279e76f7bf4b0d12431eb3abb588ef312865622d8
```

Исходная модель: [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507).
GGUF: [Bartowski, закреплённая ревизия](https://huggingface.co/bartowski/Qwen_Qwen3-4B-Instruct-2507-GGUF/blob/ae44f08e1392f39c0e474af10c3ff8355c8b6688/Qwen_Qwen3-4B-Instruct-2507-Q4_K_S.gguf).
Размер — 2 383 309 536 байт. Установщик сохраняет файл под именем
`qwen3-4b-instruct-2507-q4_k_s.gguf` и проверяет SHA-256 до замены целевого файла.
Установщик не удаляет другие GGUF автоматически. Старый файл 1.7B после
проверки основного выпуска удалён отдельной операцией.

OCR-веса загружаются при сборке отдельного образа и проверяются по SHA-256:
`ch_PP-OCRv5_det_mobile.onnx` и `cyrillic_PP-OCRv5_rec_mobile.onnx`.
При распознавании скачивание весов не выполняется. ONNX Runtime использует
только CPU и по одному потоку, CUDA и CPU memory arena выключены.

## Конфигурация

В `backend/.env.production`:

```env
LLM_PROVIDER=local
LLM_API_KEY=
LLM_BASE_URL=http://llm:8080/v1
LLM_MODEL=qwen3-4b-instruct-2507
LLM_TIMEOUT_SECONDS=75
LLM_MAX_OUTPUT_TOKENS=256
OCR_BASE_URL=http://ocr:8090
OCR_TIMEOUT_SECONDS=35
LOCAL_AI_MODELS_DIR=/opt/fitness/models
```

Старые `LLM_FALLBACK_MODELS` и `NUTRITION_VISION_MODEL` больше не используются.
Старый внешний ключ можно удалить из production `.env` после проверки запуска.

В Compose для отдельного сервиса `ocr` задано `OCR_ENGINE=ppocr` и лимит 512 МБ.
Для явного возврата Tesseract задайте этому сервису `OCR_ENGINE=tesseract`
в Compose override и пересоздайте только `ocr`; изменение переменной в API
не переключает OCR-контейнер. API-контракт `/recognize` и детерминированный
парсер при таком откате остаются прежними.

## Запуск и проверка

```bash
cd /opt/fitness/source
docker compose --env-file backend/.env.production up -d --build llm ocr api
docker compose --env-file backend/.env.production ps
docker compose --env-file backend/.env.production logs --tail=80 llm ocr api
docker stats --no-stream
```

Проверка из закрытой сети через API-контейнер:

```bash
docker compose --env-file backend/.env.production exec api \
  curl -fsS http://llm:8080/health
docker compose --env-file backend/.env.production exec api \
  curl -fsS http://ocr:8090/health
```

На компьютере разработчика:

```powershell
cd C:\fitness_prog\backend
.\.venv\Scripts\python.exe -m pytest -q tests\test_ai_analytics.py tests\test_ai_engine_llm.py tests\test_ai_context.py tests\test_nutrition_label_vision.py tests\test_llm_prompts.py
.\.venv\Scripts\python.exe -m ruff check app tests
```

После этого вручную проверьте в приложении короткий вопрос ИИ-тренеру и чёткое
фото таблицы КБЖУ. Цифры в черновике этикетки обязательно остаются редактируемыми.
У текстового ответа проверьте `source=local`, завершённость последней фразы,
русский язык и отсутствие `<think>`. Повторите запрос после прогрева и при
двух одновременных пользователях; зафиксируйте время ответа, RAM и swap.
Успешный `/health` и unit-тесты с подменённым HTTP не подтверждают качество модели.

## Диагностика

| Симптом | Что проверить |
|---|---|
| Ответ «локальная модель недоступна» | `docker compose ps llm`, затем логи `llm` и `api`. |
| `local_ai_rejected_non_local_configuration` | В `.env.production` должен быть `http://llm:8080/v1`, не внешний домен. |
| `local_ai_request_failed` | Загружена ли модель, не сработал ли лимит RAM, отвечает ли `/health`. |
| Вместо ИИ-разбора показана сводка тренировки | Проверьте сообщение о резервном ответе, `local_ai_*` и `workout_ai_interpretation_rejected` в логах. В build b10630 используется `response_format.type=json_object` с плоским `schema`. Разбор истории должен возвращать `source=local` только после проверки модельного текста; `source=data` означает сводку. |
| Вопрос о весе/питании получает отчёт о тренировках | Убедитесь, что API обновлён; запустите `tests/test_ai_analytics.py` и проверьте домен запроса. |
| «За месяц» показывает 14 дней | Обновите API; период извлекается сервером из исходного вопроса и должен быть 30 дней. |
| Этикетка не читается | Логи `ocr`, ровное фото без бликов, таблица крупно в кадре. |
| `local_ocr_failed` | Состояние `ocr`, `OCR_ENGINE`, проверка двух локальных ONNX-весов и доступность внутренней сети; при откате Tesseract — языки `rus` и `eng`. |
| Долгий ответ | Очередь до 5 секунд, общий бюджет компактного профиля 75 секунд, CPU/RAM в `docker stats`, отсутствие thinking и корректность chat template. |
| Ответ обрывается | `finish_reason`, бюджет токенов и длительность запроса; не выдавайте незавершённый ответ за успешный. |

Проверить отсутствие публичных AI-портов:

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
sudo ss -lntp
```

У `llm` и `ocr` не должно быть записей вида `0.0.0.0:8080` или
`0.0.0.0:8090`.

## Откат без потери данных

Замена ИИ не меняет схему PostgreSQL. Для временного отключения тренера
остановите только `llm`: этикетки продолжит обрабатывать независимый OCR,
пользователи, тренировки и история диалогов останутся в БД:

```bash
docker compose --env-file backend/.env.production stop llm
```

После исправления снова выполните `up -d llm api`. Не удаляйте PostgreSQL
volume и не используйте `docker compose down -v`.

После проверки основного выпуска старый файл `qwen3-1.7b-q4_k_m.gguf` удалён
с проверкой его SHA-256 и реального пути. Каталог моделей целиком не очищают.

Для отката к 1.7B восстановите предыдущую версию Compose/API: файл
`/models/qwen3-1.7b-q4_k_m.gguf`, alias и `LLM_MODEL=qwen3-1.7b`, контекст 4096.
Сначала снова загрузите файл из
[закреплённой ревизии Unsloth](https://huggingface.co/unsloth/Qwen3-1.7B-GGUF/blob/d7f544eead698dbd1f15126ef60b45a1e1933222/Qwen3-1.7B-Q4_K_M.gguf)
и проверьте SHA-256:
`b139949c5bd74937ad8ed8c8cf3d9ffb1e99c866c823204dc42c0d91fa181897`.
Затем пересоздайте `llm` и API. Такой откат восстанавливает прежнюю работоспособность,
но не исправляет известные ошибки интерпретации 1.7B.

Откат к прежнему коду не восстанавливает удалённые веса автоматически.
