# Локальный ИИ и распознавание этикеток на VPS

Production не обращается к Groq, OpenAI или другому внешнему AI API. На VPS
работают два закрытых Docker-сервиса:

- `llm`: `llama.cpp` и `Qwen3-1.7B Q4_K_M` для русских текстовых ответов
  ИИ-тренера, без генерации скрытых рассуждений;
- `ocr`: PP-OCRv5 mobile и Cyrillic mobile через RapidOCR 3.9.2 /
  ONNX Runtime 1.24.4 для чтения фото пищевой этикетки. Tesseract `rus+eng`
  остаётся в образе для явного отката.

Фото попадает во внутренний PP-OCRv5, а распознанный текст разбирает
детерминированный OCR-парсер. Фото и текст этикетки не передаются в Qwen:
черновик КБЖУ не зависит от очереди ИИ-тренера и остаётся редактируемым.
Qwen запущен только для текста, без `mmproj`. Порты `8080` и `8090`
не публикуются на VPS и доступны лишь
API в Docker-сети `ai_internal`. Код дополнительно отклоняет любой LLM URL,
который не указывает на `llm` или loopback.

## Ресурсы и ограничения

Для текущего VPS 2 vCPU / 4 ГБ RAM:

- Qwen ограничен 2,8 ГБ RAM, 2 CPU, контекстом 4096 токенов и одним запросом;
- используются два потока генерации и два потока обработки prompt,
  `batch-size=256`, `ubatch-size=64`; RAM-кэш prompt и context checkpoints
  отключены (`cache-ram=0`, `ctx-checkpoints=0`);
- reasoning отключён на сервере; запрос приложения также передаёт
  `chat_template_kwargs={"enable_thinking":false}`;
- OCR ограничен 512 МБ RAM, 1 CPU и также обрабатывает одно фото за раз;
- бюджет ответа тренера по умолчанию — 256 выходных токенов, допустимый диапазон
  настройки — 128–384; общий лимит ожидания — 60 секунд, из них очередь ждёт
  не более 5 секунд, затем приложение возвращает безопасный ответ по правилам;
- если модель недоступна, AI-тренер даёт безопасный rule-based ответ, а
  этикетка всё равно может вернуть данные детерминированного OCR-парсера.

Вопросы о боли, времени отдыха между подходами и еде после тренировки не
передаются модели: приложение отвечает проверенными детерминированными правилами.
Вывод модели также отклоняется, если он повторяет сводку приложения вместо
ответа или содержит фрагменты на другом языке.

В чате передаются до шести сообщений истории. Ограничения prompt в символах:
контекст приложения — 1500, каталог — 900, история — 1200, вопрос — 1800.
Для отдельного анализа блок проверяемых данных ограничен 2400 символами.
Расширение этих лимитов не увеличивает серверный контекст 4096 токенов.

Сервер классифицирует запросы по доменам `workout_progress`, `strength`,
`measurements`, `weight`, `nutrition`, `recovery`, `safety`, `general`. Для
аналитического домена в Qwen передаются только ограниченные агрегаты выбранного
периода. «Месяц» означает 30 дней; явный период ограничен 1–365 днями. Если в
домене нет фактов, модель не вызывается: пользователь получает один уточняющий
вопрос. Тоннаж считается единым backend-правилом: `per_hand × 2`, `total × 1`,
а повторы без веса и интервалы по времени остаются отдельными метриками.

Qwen3-1.7B выбран после сравнительных запросов на VPS: ответы контрольного
набора занимали 5,2–31,9 секунды. Первоначальный кандидат Qwen3.5-2B отклонён:
он подставлял жим вместо становой тяги и выдумывал факты в вопросе по каталогу.
Эти замеры ограниченного набора не гарантируют скорость и качество всех запросов.
Проверка новой конфигурации после production-выпуска остаётся обязательной.

На шести реальных фото новый OCR точно прочитал 15 из 21 проверяемого значения;
пиковое потребление памяти было около 320 МБ при лимите 512 МБ. На молоке
остались пропуски белка и жира, фото курицы не читалось; у десерта энергия
449,1 ккал рассчитана из прочитанных кДж. Числа из состава не подставлялись
в КБЖУ. Это ограниченный проверочный набор, а не обещание полной точности.

Размер GGUF не равен рабочему потреблению памяти. Проверьте тариф, если
доступная память устойчиво ниже 500 МБ, swap постоянно растёт или AI регулярно
не укладывается в timeout.

## Первая установка модели

Модель не хранится в Git. Интернет нужен один раз для загрузки закреплённой
GGUF-конвертации модели Qwen, после этого inference полностью локален.

```bash
cd /opt/fitness/source
sudo sh scripts/install-local-ai-model.sh /opt/fitness/models
sha256sum /opt/fitness/models/qwen3-1.7b-q4_k_m.gguf
```

Ожидаемая SHA-256:

```text
b139949c5bd74937ad8ed8c8cf3d9ffb1e99c866c823204dc42c0d91fa181897
```

Исходная модель: [Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B).
GGUF: [Unsloth, закреплённая ревизия](https://huggingface.co/unsloth/Qwen3-1.7B-GGUF/blob/d7f544eead698dbd1f15126ef60b45a1e1933222/Qwen3-1.7B-Q4_K_M.gguf).
Размер — 1 107 409 472 байт. Установщик сохраняет файл под именем
`qwen3-1.7b-q4_k_m.gguf` и проверяет SHA-256 до замены целевого файла.

OCR-веса загружаются при сборке отдельного образа и проверяются по SHA-256:
`ch_PP-OCRv5_det_mobile.onnx` и `cyrillic_PP-OCRv5_rec_mobile.onnx`.
При распознавании скачивание весов не выполняется. ONNX Runtime использует
только CPU и по одному потоку, CUDA и CPU memory arena выключены.

## Конфигурация

В `backend/.env.production`:

```env
LLM_PROVIDER=local
LLM_API_KEY=
LLM_BASE_URL=http://llm:8080/v1
LLM_MODEL=qwen3-1.7b
LLM_TIMEOUT_SECONDS=75
LLM_MAX_OUTPUT_TOKENS=256
OCR_BASE_URL=http://ocr:8090
OCR_TIMEOUT_SECONDS=35
LOCAL_AI_MODELS_DIR=/opt/fitness/models
```

Старые `LLM_FALLBACK_MODELS` и `NUTRITION_VISION_MODEL` больше не используются.
Старый внешний ключ можно удалить из production `.env` после проверки запуска.

В Compose для отдельного сервиса `ocr` задано `OCR_ENGINE=ppocr` и лимит 512 МБ.
Для явного возврата Tesseract задайте этому сервису `OCR_ENGINE=tesseract`
в Compose override и пересоздайте только `ocr`; изменение переменной в API
не переключает OCR-контейнер. API-контракт `/recognize` и детерминированный
парсер при таком откате остаются прежними.

## Запуск и проверка

```bash
cd /opt/fitness/source
docker compose --env-file backend/.env.production up -d --build llm ocr api
docker compose --env-file backend/.env.production ps
docker compose --env-file backend/.env.production logs --tail=80 llm ocr api
docker stats --no-stream
```

Проверка из закрытой сети через API-контейнер:

```bash
docker compose --env-file backend/.env.production exec api \
  curl -fsS http://llm:8080/health
docker compose --env-file backend/.env.production exec api \
  curl -fsS http://ocr:8090/health
```

На компьютере разработчика:

```powershell
cd C:\fitness_prog\backend
.\.venv\Scripts\python.exe -m pytest -q tests\test_ai_analytics.py tests\test_ai_engine_llm.py tests\test_ai_context.py tests\test_nutrition_label_vision.py tests\test_llm_prompts.py
.\.venv\Scripts\python.exe -m ruff check app tests
```

После этого вручную проверьте в приложении короткий вопрос ИИ-тренеру и чёткое
фото таблицы КБЖУ. Цифры в черновике этикетки обязательно остаются редактируемыми.
У текстового ответа проверьте `source=local`, завершённость последней фразы,
русский язык и отсутствие `<think>`. Повторите запрос после прогрева и при
двух одновременных пользователях; зафиксируйте время ответа, RAM и swap.
Успешный `/health` и unit-тесты с подменённым HTTP не подтверждают качество модели.

## Диагностика

| Симптом | Что проверить |
|---|---|
| Ответ «локальная модель недоступна» | `docker compose ps llm`, затем логи `llm` и `api`. |
| `local_ai_rejected_non_local_configuration` | В `.env.production` должен быть `http://llm:8080/v1`, не внешний домен. |
| `local_ai_request_failed` | Загружена ли модель, не сработал ли лимит RAM, отвечает ли `/health`. |
| Вместо ответа повторяется сводка тренировки | Убедитесь, что API и `llm` используют alias `qwen3-1.7b`; проверьте факты и историю в prompt, затем повторите исходный вопрос. |
| Вопрос о весе/питании получает отчёт о тренировках | Убедитесь, что API обновлён; запустите `tests/test_ai_analytics.py` и проверьте домен запроса. |
| «За месяц» показывает 14 дней | Обновите API; период извлекается сервером из исходного вопроса и должен быть 30 дней. |
| Этикетка не читается | Логи `ocr`, ровное фото без бликов, таблица крупно в кадре. |
| `local_ocr_failed` | Состояние `ocr`, `OCR_ENGINE`, проверка двух локальных ONNX-весов и доступность внутренней сети; при откате Tesseract — языки `rus` и `eng`. |
| Долгий ответ | Очередь до 5 секунд, общий бюджет 60 секунд, CPU/RAM в `docker stats`, отсутствие thinking и корректность chat template. |
| Ответ обрывается | `finish_reason`, бюджет токенов и длительность запроса; не выдавайте незавершённый ответ за успешный. |

Проверить отсутствие публичных AI-портов:

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
sudo ss -lntp
```

У `llm` и `ocr` не должно быть записей вида `0.0.0.0:8080` или
`0.0.0.0:8090`.

## Откат без потери данных

Замена ИИ не меняет схему PostgreSQL. Для временного отключения тренера
остановите только `llm`: этикетки продолжит обрабатывать независимый OCR,
пользователи, тренировки и история диалогов останутся в БД:

```bash
docker compose --env-file backend/.env.production stop llm
```

После исправления снова выполните `up -d llm api`. Не удаляйте PostgreSQL
volume и не используйте `docker compose down -v`.

При выпуске старые файлы `qwen2.5-3b-instruct-q4_k_m.gguf` и
`qwen2.5-1.5b-instruct-q4_k_m.gguf` сохраняют до проверки новой модели в живом
приложении. Только после успешной проверки допускается удалить эти два точных
файла, предварительно проверив путь и отсутствие ссылок из запущенных контейнеров.
Каталог моделей целиком и новый GGUF не удаляют.

Для отката восстановите предыдущие Compose/API-настройки и перезапустите `llm`
с прежним файлом и alias. Если старый 3B GGUF уже удалён, повторно скачайте его
из [официального Qwen2.5-3B GGUF](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF)
и проверьте SHA-256
`626b4a6678b86442240e33df819e00132d3ba7dddfe1cdc4fbb18e0a9615c62d`
до запуска. Откат к прежнему коду не восстанавливает удалённые веса автоматически.
