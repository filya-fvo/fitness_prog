## Предлагаемое поведение конструктора

### Основные параметры

- Сохранить два шага «Основа» и «Дни», создание только личной программы.
- Сохранить 1–7 дней, 1–12 уникальных упражнений на день, 1–8 подходов. Composer получает явные ограничения вместо молчаливого расширения до своих 20/20.
- Упражнения можно добавлять, заменять, менять порядок, открывать технику; групповая структура сохраняется атомарно. Не удалять участника связки молча.
- Черновик должен сохранять новые поля/методы/группы по аккаунту, читать старый формат безопасно, объяснять недоступное хранилище.

### Ввод без борьбы с клавиатурой

- Каждое числовое поле имеет локальный строковый черновик: очистка остаётся пустой; при наборе нет clamp к минимуму/максимуму. Некорректное значение не отправляется на сервер и получает адресную ошибку при завершении редактирования/сохранении.
- Рядом с ручным вводом — небольшие пресеты и кнопки «−»/«+» с минимумом 44×44, понятными именами, 16 px полями и клавиатурной доступностью. Пресеты являются явным действием, не заменяют ввод незаметно.
- Отдых: 0–300 с для личных обычных подходов, как минимальное расширение прежнего 15–300. Пресеты «Без отдыха», 30, 60, 90, 120 с. Максимум не увеличивать без необходимости. У связок/частей сохраняются существующие 0–600 с.
- Длительность программы также не перескакивает на 1/52 при очистке. Пустые обязательные значения не превращать через Number("") в ноль.
- Повторы обычного упражнения: два поля «От» и «До», например 12 и 15 → видимая цель «12–15 повторов». При равных границах отображается одно число. Проверка целых положительных значений и min≤max.
- Время: отдельное поле «Время работы», пресеты и выбор единицы секунд/минут с однозначным сохранением в секундах. Отдых и время выполнения никогда не смешиваются. Время работы не равно 0; 0 допустим именно для отдыха.
- Вес: необязательная плановая цель с подписью «Укажу при выполнении»; русская запятая, разумный шаг и формат общего/одной гантели по действующим правилам. Не записывать плановый вес как уже выполненный результат.
- Режим цели: «Повторы», «Вес и повторы», «Время». По умолчанию подходит каталожному типу. Доступность вариантов проверяется существующей моделью выполнения; у cardio machine сохраняется собственная форма параметров. Нельзя показать режим, который старт или запись результата игнорируют. Если безопасный произвольный переход требует нового runtime-контракта, это отдельный зафиксированный шаг B04a, а не UI-only selector.

### Сложные методы

- Включить существующие суперсеты, трисеты, круги, дропсеты и кластеры. Это предел фразы «и т.д.» на первом этапе; не придумывать новый rest-pause runtime kind.
- Связки: уникальные соседние участники, число раундов, переход между упражнениями и отдых после круга. Sets участников согласованы с rounds. Draft редактирования связки блокирует общее сохранение, пока не завершён/отменён.
- Дроп/кластер: выбор конкретного, последнего или всех подходов; 2–8 частей; допустимые веса и паузы, убывающий вес дропа/одинаковый кластера, последняя внутренняя пауза ноль. Использовать текущую load-type validation.
- Диапазон повторов относится к обычной цели упражнения. У частей дропа/кластера сохраняется текущая точная цель повторов; диапазон для каждой части — отдельное расширение, не маскировать его строкой в целочисленном поле.
- Не переносить CompoundSetEditor в конструктор: он записывает факты выполнения, а не план.

## Контракты и совместимость

PersonalProgramInput сейчас содержит только id/sets/reps/rest; backend также сохраняет только их. UI-only исправление методов потеряло бы данные.

- Сохранить старые поля и допустимость старого payload. Опциональные groups на уровне дня; set_methods на уровне упражнения — действующие WorkoutGroup/WorkoutSetMethod.
- Для явной обычной цели добавить типизированный optional target (дискриминируемая цель повторов/веса/времени) в personal payload и план. Точное имя/структуру зафиксировать в B02 до RED-теста во всех Pydantic/Zod/TS контрактах. Не переопределять смысл suggested_weight как исторической подсказки.
- Группы и методы проверять общими валидаторами topology/weights/load type. Не сохранять конфигурацию группы отдельно у каждого участника.
- JSON Program.structure позволяет добавить поля без обязательной SQL-миграции. Если исследование выявит DB enum/constraint, создать новую миграцию; существующие не переписывать.
- Сборка плана, preview, started snapshot, browser drafts, timed modal, preparation fingerprint и session snapshot key должны учитывать новые цели. Поля отсутствуют у старого плана → прежний snapshot key не менять, чтобы не сломать активную тренировку.
- Явные новые цели и нулевой отдых не заменяются фазой/историей. Старые phased-программы без новой явной конфигурации сохраняют прежнее поведение. На экране объяснить: «Явно заданные цели сохраняются; фаза даёт рекомендации».
- Начатые/завершённые тренировки не пересчитывать. Подсказка/план никогда не становятся выполненным подходом автоматически. Сохранённый факт всегда старше по приоритету, чем новая цель.
- Первоначальное фактическое значение диапазона: сохранять существующий принцип редактируемой подсказки (нижняя граница диапазона там, где требуется число), рядом всегда показывать весь диапазон; отсутствие отметки выполнения сохраняется. Проверить это в runtime, не только на карточке плана.

## Работа агентов, коммиты и публикация

Ведущий держит единый tracker, интеграцию, команды runtime и commits. Агент-исследователь ограничивает контракт/риски текущего шага; агент-исполнитель получает только текущую задачу и files; независимый reviewer проверяет готовый diff/примеры/тесты. Никакого одновременного изменения общей модели несколькими агентами. Следующая реализация начинается после GREEN/review/commit предыдущей.

Публикация WEB — после проверенного этапа по действующему разрешению владельца: итоговый diff/тесты → commit/push production branch → backup с проверкой восстановления → ff-only/rebuild/migrations/up → services/API/site/затронутый live-read сценарий. Промежуточный commit не считать публикацией. Нельзя выпускать промежуточный UI с неподдерживаемым backend. Android — отдельный следующий этап после WEB, без побочного APK выпуска.

Если лимит токенов остановит работу, сохранить точный HEAD/следующий шаг/ошибки/проверки и использовать актуальное указание владельца о продолжении.
