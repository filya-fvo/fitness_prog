# Личные изменения программы и сложные методы выполнения

Дата: 19.10.2026. Статус: предложение для подготовки реализации; продуктовый код не изменён.

## 1. Цель и границы

Пользователь занимается по существующей программе «Чередование акцентов» и хочет:

- добавлять упражнения из каталога, например пресс, не собирая программу заново;
- сохранять изменения только для себя;
- использовать дроп-сеты, суперсеты, трисеты, круги и кластеры;
- получать правильные подсказки перехода, таймеры, историю и расчёты нагрузки;
- сначала получить полностью проверенный web, затем те же возможности в Android.

Основной сценарий: подготовка → редактирование → сохранение → старт → выполнение → история.
Структуру меняем до старта. Новое редактирование состава посреди выполнения в этот выпуск не входит;
существующие замены остаются и не должны повреждать записанные результаты.

Принятые для плана предположения: два режима сохранения — «Только эта тренировка»
и «Мои следующие тренировки этого дня программы»; второй применяется во всех фазах нагрузки.
Это проектные решения, а не уже существующие возможности приложения.

## 2. Проверенная основа

- `planned_workout.py` и `WorkoutPlanOverride` сохраняют только замены на дату;
  запись расходуется при создании тренировки. Постоянного слоя персональных изменений нет.
- `PersonalProgramBuilderPage.tsx`, `Program.owner_id`, `/programs/my` уже реализуют свои программы.
  Не создавать второй конструктор и не требовать ручного копирования общей программы.
- В `Workout.plan` сохраняется JSON-снимок. Подход идентифицируется сочетанием
  `(workout_id, exercise_id, set_number)`. Одно упражнение в плане сейчас не повторяется.
- `update_workout_plan` сопоставляет замены по `order`; перестановка упражнений требует
  устранения такого сопоставления до появления нового редактора порядка.
- Текущие session/completion/load hints и несколько SQL-агрегаций считают обычные подходы.
  Запись «100 кг × 12» вместо трёх кластеров по четыре исказит историю и расчётный 1ПМ.
- Android использует общий React через pinned `shared/fitness_prog`, собственные SQLite/outbox
  и `offlineProgramStart.ts`. Простого обновления интерфейса недостаточно.

На момент изучения основной checkout — `85d5974`, последний опубликованный shared по Android
AGENTS/HANDOFF — `a2cb5cc`, native HEAD — `cb4cbcb`. Это локальные сведения, не live-проверка VPS.
Исследованы также исходники pinned shared. Перед реализацией сверить GitHub/VPS и выбрать
последнюю согласованную основу, содержащую уже выпущенный offline/android_sync.
В текущем основном checkout этих модулей ещё нет. Чужие изменения не сбрасывать.

## 3. Выбор архитектуры

Рекомендуется персональный слой изменений поверх закреплённой версии программы.
Он сохраняет программу, чередование акцентов, календарь и указатель следующего дня.
Альтернативы: копия всей программы проще сначала, но требует переноса состояния и создаёт
расхождения версий; только правки на дату не закрывают постоянное добавление пресса.

Сборка плана: исходный день + персональные изменения → фаза/готовность/восстановление
по существующим правилам → правки на дату → неизменяемый снимок начатой тренировки.
Не переопределённые пользователем параметры продолжают следовать исходной фазе.
Явные настройки метода, например четыре повтора в кластере, не заменяются общим диапазоном фазы.
При конфликте готовности с явно заданной интенсивностью показать его до старта;
не повышать автоматически вес или сложность метода.

Персональные изменения привязаны к `(user_id, program_id, day_index)` и версии исходного дня.
Они хранят добавления/удаления/порядок/изменённые параметры, а не замороженную копию фазы.
Переход на другую версию программы не переносит их молча. Уже начатые и завершённые
тренировки не пересчитываются. Сброс личных изменений возвращает исходный будущий план.
Если уже есть правка на дату, её приоритет виден в preview; сброс постоянных правок её не удаляет.
Перенос даты использует существующий сценарий переноса, сохраняя правку либо явно сообщая конфликт.

Оставить запрет повторного `exercise_id` внутри одного дня: для дропов и кластеров не нужны
дубликаты упражнения. Группы ссылаются на `exercise_id`, имеют собственный UUID и порядок.
Замену упражнения проводить по явному соответствию исходного/нового ID, не по позиции.
Удаление/замена участника группы обновляет ссылки атомарно либо возвращает понятную ошибку.

## 4. Методы и единицы учёта

| Метод | Что задаёт пользователь | Что означает выполнение |
|---|---|---|
| Обычный | подходы, повторы/время, отдых | один результат на подход |
| Дроп-сет | выбранные подходы, ступени: вес и повторы, пауза перехода | один составной подход с отдельными результатами ступеней |
| Кластер | выбранные подходы, число мини-подходов, повторы, общий вес, короткая пауза | один составной подход с результатами мини-подходов |
| Суперсет | два упражнения, число раундов, переход и отдых после раунда | A1 → B1 → отдых → A2 → B2 |
| Трисет | три упражнения, раунды, переход и отдых | A1 → B1 → C1 → отдых |
| Круг | от двух упражнений, раунды, переход и отдых | все участники по порядку, затем отдых |

Пример кластера: один подход `100 кг · 4 + 4 + 4`, между частями, например, 20 секунд
по выбору пользователя. Это три мини-подхода внутри одного, а не три полных подхода по 12.
Пример дропа: `30×10 → 25×8 → 20×8`; выполненный объём — 660 кг·повторов.
Это примеры данных и поведения интерфейса, не автоматическое назначение нагрузки.

Упражнение может принадлежать одной группе; группы не вложены и не пересекаются.
Разрешить дроп или кластер внутри участника группы: сначала закончить его части,
потом перейти к следующему участнику. Одновременный дроп и кластер одного подхода не поддерживать.
По умолчанию дроп назначается последнему подходу; кластер — выбранным пользователем подходам.
Количество подходов участников равно числу раундов группы; при объединении разных значений
показать предварительный результат и запросить выбор числа раундов, не менять его скрыто.

Границы первой версии: 1–20 упражнений дня, 1–20 подходов/раундов,
2–8 частей дропа/кластера; отдых 0–600 секунд. Суперсет — ровно 2, трисет — ровно 3,
круг — 2–20 участников. Для ступеней дропа вес положительный и строго убывает;
у кластера вес одинаковый, повторы могут различаться по факту выполнения.
Дроп/кластер применяются к упражнениям с весом и повторами; обычные участники круга
могут учитывать время. Для неприменимого метода показывать короткое объяснение.
Уже сохранённые legacy-значения вне новых границ не обрезать при чтении.

Результаты частей хранить структурированно, не в заметке. Родительский `WorkoutSet`
сохраняется; новые дочерние записи имеют стабильные UUID и порядковые номера.
Статусы частей: pending/completed/skipped. Любая выполненная часть сохраняет объём,
даже если тренировка завершена частично. Составной подход завершён, когда нет pending
и есть хотя бы одна completed; пропуски отдельно видны в истории. Полностью пропущенный
подход разрешает переход дальше, но не становится выполненным подходом.

В первой версии 1ПМ, силовые рекорды и обычная подсказка рабочего веса берутся только из
обычных непрерывных подходов. Дропы/кластеры видны в дневнике и объёме, но не выдаются
за обычные рекорды. Внутри суперсета обычный подход остаётся обычным.
Счётчик подходов считает родителей, а не каждую часть; число частей показывается отдельно.
Регулярность/соревнования не получают дополнительных тренировок или баллов из-за частей.

## 5. Таймер и переходы — обязательный контракт

### Четыре независимых смысла времени

1. Общее время тренировки — существующий секундомер от старта до завершения.
2. Время выполнения timed-упражнения — его собственный результат, не отдых.
3. Пауза внутри дропа/кластера или между упражнениями группы — короткий переход.
4. Отдых между полными подходами/раундами и перед следующим блоком — восстановление.

Общее время включает работу и паузы, как и сейчас. Одновременно активна одна пауза;
секундомер тренировки продолжает идти. Нельзя запускать два отдыха за одно действие.
Существующие ограничения для timed-упражнений сохранить, не приравнивать секундомер к отдыху.

### Таблица решений

| Подтверждённое действие | Следующая работа | Таймер |
|---|---|---|
| Обычный подход, есть следующий подход этого упражнения | следующий подход | обычный отдых упражнения |
| Промежуточная ступень дропа | следующая ступень этого подхода | переход ступени, по умолчанию 0 |
| Промежуточная часть кластера | следующая часть этого подхода | короткая пауза кластера |
| Последняя часть составного подхода вне группы, есть следующий подход | следующий полный подход | обычный отдых упражнения |
| Подход участника A, далее участник B группы | B того же раунда | переход группы, по умолчанию 0 |
| Последний участник раунда, есть следующий раунд | первый участник следующего раунда | отдых группы |
| Последний подход/раунд блока, далее другой блок | первый подход следующего блока | отдых завершённого блока, один раз |
| Последняя работа тренировки | экран итогов/кнопка завершения | отдых не запускается, завершение остаётся явным |
| Правка уже записанных повторов/веса | текущая работа | активный таймер не меняется |

Правило приоритетов: незаконченные части → следующий участник группы → следующий раунд
→ следующий блок → конец. Внутригрупповой отдых участника не добавляется к отдыху группы.
Последняя часть кластера внутри A ведёт к B по переходу группы, а не к длинному отдыху A.
После последнего раунда не складывать «отдых раунда» и «отдых блока».
Если следующий блок отсутствует, не запускать паузу «на всякий случай».
Отдых завершённого блока — `round_rest_sec` для группы, `rest_sec` последнего упражнения
для одиночного блока. Это одно значение, а не сумма двух пауз.

Схему таймера перед стартом показывать словами: «4 повтора → 20 с → 4 повтора →
20 с → 4 повтора → 120 с → следующий подход». Для связки: «Бицепс → трицепс → 90 с отдыха».
Нулевой переход сразу предлагает следующую работу без мигающего таймера «0».
Изменение пауз редактирует preview, не результаты уже начатой тренировки.

### Запуск и окончание

- Действие «Готово» сначала надёжно сохраняет локальный результат и курсор,
  затем применяет одно решение перехода. Ошибка durable-сохранения не продвигает выполнение.
- Пауза отсчитывается от момента подтверждения пользователем, а не от ответа сети.
  Сетевой ответ, повтор запроса, двойное нажатие и повторный рендер не создают новую паузу.
- По истечении паузы один сигнал/вибрация и предложение следующего шага.
  Таймер не отмечает следующий подход выполненным, не запускает его timed-результат
  и не запускает новый отдых самостоятельно.
- Настройка автоперехода управляет переходом интерфейса, не видом/длиной отдыха.
  При включённой настройке следующая работа открывается после окончания паузы, при нулевой —
  сразу. При выключенной остаётся явная кнопка следующего шага; логический следующий шаг тот же.
  Не добавлять старый отдельный пятисекундный отсчёт автоперехода поверх рассчитанной паузы.
- «Закончить отдых» меняет только паузу. «Пропустить часть/участника» — отдельное действие
  с видимым статусом; нулевой или пропущенный результат не добавляет объём.
  Сам пропуск невыполненной работы не запускает отдых: вычисляется следующая работа
  и предлагается явное продолжение. Пропуск не стирает ранее выполненные части.
- Досрочное выполнение во время активного отдыха требует явного окончания текущей паузы;
  редактирование старого результата её не прерывает. Никакого скрытого наложения таймеров.
- Отмена последнего выполнения отменяет лишь порождённую им ещё актуальную паузу;
  после новых действий не откатывает весь прогресс. Изменение настройки длительности
  относится к следующим паузам; изменение текущей — отдельное действие «Добавить 15 с».

### Сворачивание, перезагрузка, офлайн

Хранить `transition_id`, исходное действие, тип паузы, целевой шаг, `started_at`,
`ends_at`, выбранную длительность, курсор block/round/exercise/set/part, версию снимка
и owner. Оставшееся время вычислять по deadline; `setInterval` только перерисовывает экран.
Для текущего процесса использовать монотонные часы; для восстановления — сохранённые timestamps.
Изменение системных часов/часового пояса не должно запускать новую паузу или давать
отрицательное/неограниченное время: проверить расхождение, восстановить с ограничением
исходной длительностью и предложить явное продолжение при неоднозначности.

После возврата до deadline показать остаток; после deadline — «Отдых завершён» и тот же
следующий шаг. Не проигрывать очередь пропущенных сигналов и не выполнять шаги в фоне.
В нескольких вкладках одна активная сессия владеет сигналами; восстановление в другой
вкладке не даёт двойной вибрации. Между устройствами таймер не управляет чужим экраном.
При смене аккаунта старые таймер/цели/результаты не показываются новому владельцу.

Web не гарантирует фоновый звук при закрытом браузере: точность восстановления времени
обязательна, фоновое системное уведомление web не входит в эту функцию.
На Android SQLite сохраняет курсор/паузы до подтверждения интерфейса; проверить process death,
cold restart, экран блокировки и фактическую доступность сигнала. Системные workout-reminders
не использовать для пауз подходов; новый background service/разрешение не добавлять без отдельного решения.

## 6. Сохранение, конфликты и совместимость

Добавить revision персональных правок и снимка выполнения. При устаревшей записи — 409,
локальные результаты остаются доступны; «последний ответ победил» недопустим.
Обычные старые payload продолжают работать с обычными тренировками. Новый составной
результат требует версии формата и идентификатора операции для идемпотентного повтора.
Legacy-клиент не должен стереть части или группу при сохранении урезанного JSON.
Старый web/Android получает безопасный отказ записи нового формата с просьбой обновления,
а не молчаливую конверсию в обычные подходы. Проверить REST и Android sync dispatch.
Офлайн-очередь старого APK сохраняется; конфликт не удаляет её и не блокирует несвязанные обычные записи.

В web подготовленные планы и локальные изменения имеют owner и revision, входят в существующую
очередь; можно редактировать ранее загруженный день без сети. Сохранение показывает
«На устройстве, ожидает синхронизации», а не обещает уже обновлённый сервер.
После изменения личного дня инвалидируются связанные prepared-планы, preview и подсказки.
Fingerprint офлайн-подготовки должен учитывать revision правок, а не только календарь.
Изменения на сервере после офлайн-старта дают конфликт с сохранённым фактом тренировки,
не заменяют его результат текущим шаблоном. Редактирование без каталога/плана объясняет,
что сначала нужно загрузить данные, не создаёт пустую тренировку.

Android: общий бизнес-код переносится только обновлением проверенного shared pin.
Native адаптер поддерживает те же схемы, durable SQLite и outbox; Dexie остаётся проекцией.
Обновление APK поверх старой версии сохраняет session, дневник и неотправленную очередь.

## 7. Критерии приёмки

1. Пользователь A добавляет пресс в день 1 «Чередования акцентов»; следующий день 1
   содержит пресс, дни 2–4 и программа пользователя B неизменны. Календарь/фазы не сброшены.
2. Разовая правка исчезает из будущих повторений, постоянная сохраняется; сбросы различимы.
3. Бицепс и добавленное упражнение образуют суперсет с правильным порядком раундов.
   Аналогично проверены трицепс, трисет и круг.
4. Дроп 30×10/25×8/20×8 даёт 660 кг·повторов и не создаёт три обычных рекорда.
5. Кластер 100×(4+4+4) даёт 1200 кг·повторов; при паузе 20 с и отдыхе 120 с
   перед следующим полным подходом последовательность пауз — 20/20/120.
   Если это последняя работа тренировки — только 20/20; внутри суперсета действует переход группы.
6. Незавершённые/пропущенные части, отмена, повтор запроса и ручное завершение не теряют факты.
7. История, dashboard, AI-факты, подсказки и соревнования согласованы по смыслу.
