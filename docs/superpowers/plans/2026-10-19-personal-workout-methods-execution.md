# Инструкция исполнителю: персональная программа и сложные подходы

Прочитай [описание поведения](../specs/2026-10-19-personal-workout-methods-design.md)
и [план W0–W10 / A1–A4](2026-10-19-personal-workout-methods.md), затем актуальные AGENTS.
Это инструкция для будущего запуска реализации. Сейчас подготовлены документы.

## Порядок работы

1. Сначала web целиком: W0 → W1 → … → W10. Android начинается только после web-приёмки.
2. Внутри каждого этапа выбери один проверяемый результат и сначала тест его поведения.
3. Реализуй минимальный связный scope и проверь. Если ошибок нет — переходи к пункту 5.
4. Только если найдена ошибка: установи причину, исправь и повтори упавшие и затронутые проверки до успеха. Не ослабляй assertions ради зелёного результата. Успешные проверки без новых изменений и причин не повторяй.
5. Проверь итоговый diff, обнови затронутые документы и сделай отдельный коммит своих файлов.
6. Запиши SHA и доказательства проверки. Только затем приступай к следующему этапу.
7. Если ошибка найдена после коммита, отдельный fix-коммит с воспроизведением и проверкой;
   не смешивай её со следующей функцией.

Правило: **сделал → проверил → если ошибок нет, закоммитил**.
При ошибке: **исправил → перепроверил → после успеха закоммитил**.

Веди один журнал прогресса: этап, что сделано, какие проверки действительно запущены,
ошибки/исправления, итоговый SHA, что осталось проверить. Не заявляй PASS по старому отчёту,
невоспроизведению, пропуску или browser-тесту вместо installed Android.

## Что нельзя потерять

- Общая программа других пользователей, личный календарь, чередование фаз и история неизменны.
- Добавление пресса работает без создания новой программы; постоянное и разовое применение различимы.
- Дроп/кластер — отдельные структурированные части, а не текст заметки или фиктивные суммарные повторы.
- Суперсет/трисет/круг исполняются по раундам, а не всеми подходами одного упражнения подряд.
- Старые web/APK и неотправленные очереди не стирают новый формат.
- Shared-код один: сначала проверенный upstream commit, затем Android pin/manifest и native gates.

## Отдельное обязательство по таймеру

До UI реализуй и проверь таблицу переходов из раздела 5 spec.
Различай паузу между частями, переход между упражнениями, отдых после раунда и после блока.
Таймер не должен дважды отдыхать после одного события и никогда не выполняет работу за пользователя.

Обязательные примеры: кластер 3×4 перед следующим полным подходом — 20/20/120 с,
в конце тренировки — только 20/20; суперсет A/B на два раунда —
A1→B1→90 с→A2→B2→конец без отдыха. Кластер внутри A после последней части ведёт к B,
не запускает обычный длинный отдых A. Это тестовые настройки, не предписание тренировочной нагрузки.

Проверь нулевые паузы, skip/undo, правку старого результата, активный отдых, двойной submit,
позднюю сеть, autoAdvance on/off, reload, background, deadline expiry, офлайн и смену владельца.
Остаток считай от сохранённого deadline, не по числу срабатываний interval.
На Android отдельно докажи восстановление из SQLite после завершения процесса.

## Завершение и выпуск

При реализации согласованных функций действует постоянное разрешение владельца на выпуск,
с условиями актуальных AGENTS/runbook: зелёные проверки, commit/push, проверенный backup/restore,
VPS update и live-проверка. Подготовка этих документов сама по себе ничего не публикует.

Android выпускай только после A1–A4 штатным publisher с прежним локальным ключом,
монотонной версией и проверкой установки поверх предыдущей версии. Не распространяй private test APK.
Не запускай рассылки, seed/reset и не вмешивайся в пользовательский BlueStacks/OpenVPN.

В итоговом отчёте перечисли реализованные возможности, web/native SHA, APK-версию,
реально выполненные проверки и открытые ограничения устройства. Не называй всё завершённым,
если обязательный gate остался непроверенным.
