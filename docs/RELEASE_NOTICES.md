# Анонсы обновлений и выжимка изменений

Решение владельца от 29.10.2026: после проверок и фактической публикации
совместного WEB/APK-выпуска отправлять всем действующим пользователям основные
нововведения и исправления через выбранный канал. Telegram получает текст со
ссылкой https://app.filfitclub.ru/android/latest.apk, браузер — существующий
Web Push. При выборе Android новая системная push-служба не подключается.

Во всех версиях — WEB, Telegram Mini App и Android — при следующем открытии
Главной показывается краткая выжимка изменений отдельным оверлеем. Пользователь
закрывает его после прочтения. В одном окне собраны все непрочитанные выпуски,
от новых к старым; уже прочитанные не повторяются. Список фиксируется на время
показа. Закрытие подтверждает только показанные разделы: новые поздние выпуски
или незагруженные страницы остаются непрочитанными до следующего открытия. Вход, обязательные документы, открытая форма,
активная тренировка и уже открытый диалог не прерываются. Отдельной карточки
уведомления об обновлении в интерфейсе нет. Отметка прочтения не отменяет
ожидающую внешнюю отправку в Telegram или браузер.

## Перед отправкой

1. Завершить применимые проверки, независимый review, WEB/VPS-выпуск с
   backup/проверкой восстановления и проверку точного original-key APK на
   эмуляторе и настоящем телефоне. Сохранить источник, shared SHA и доказательства.
2. Опубликовать APK штатным publisher. Проверить публичные metadata, полную
   загрузку, SHA, прежнюю подпись, production API, Range и сохранность старых APK.
3. Подготовить короткий UTF-8 файл с главными нововведениями и исправлениями.
   Не включать тестовые результаты, личные сведения, секреты или обещания
   непроверенных возможностей. Ссылку на APK Telegram-доставка добавляет сама.
4. Выбрать постоянный ключ выпуска и существующего администратора. В production не создавать
   тестовых аккаунтов и тестовых кампаний. Уникальность версии/SHA APK защищает
   от повторной кампании под другим ключом; существующий ключ с другим текстом
   отклоняется. Одинаковый повтор не добавляет получателей и не сбрасывает итоги.

## Preview и публикация

CLI запускается внутри актуального API-образа с существующими production
настройками. Файл текста должен быть доступен в контейнере, например
`/app/data/release-summary.txt`. Используйте проверенные значения metadata:

```sh
python scripts/publish_release_notice.py \
  --release-key KEY --title 'Обновление FilFit' \
  --message-file /app/data/release-summary.txt \
  --apk-version VERSION --apk-sha256 SHA256 \
  --source-commit NATIVE_SHA --shared-commit WEB_SHA \
  --actor-id ADMIN_UUID
```

Без `--publish` это только preview. Он сверяет фиксированные публичные
`latest.json` и APK, повторно читает metadata после проверки bytes и выводит
только общее число и количество получателей по каналам. Адреса, токены и
получатели в вывод не попадают. Native SHA и WEB/shared SHA различаются.

После успешного preview добавить к тому же вызову
`--publish --expected-users PREVIEW_TOTAL`. Это создаёт сохранённый список
получателей и очередь; отправку выполняет существующий worker. Прямое решение
владельца разрешает итоговый анонс проверенного выпуска без повторного согласия,
но не посторонние/тестовые рассылки или повтор старых кампаний.

Worker повторно проверяет выбранный канал и удаление аккаунта перед внешней
отправкой. Android имеет приоритет над прежним выбором Telegram/browser.
Недоступный канал не подменяется другим; тихие часы откладывают внешнюю отправку.
Подтверждённые, частичные и неопределённые отправки не повторяются автоматически:
после потери ответа удалённая сторона уже могла принять сообщение.

```sh
python scripts/publish_release_notice.py --release-key KEY --status
```

Записать отдельные результаты: `sent`, `partial`, `unknown`, `unavailable`,
`skipped`, ожидающие `pending`/`awaiting_open`, прочитанные Android `seen`;
`overlay_seen`/`overlay_unread` учитывают чтение независимо от внешней доставки.
Не выдавать ожидание открытия, недоступность или неопределённость за доставку.
Не перезапускать неизвестную отправку вслепую. Идентификаторы получателей и сырые
журналы не публиковать; в итоговом отчёте достаточно агрегатов.

## Проверка фактически запущенной версии

WEB перед показом сверяет существующий compiled `__FITNESS_BUILD_ID__` с
актуальным `/version.json` через existing updater. Старый или неизвестный build
откладывает показ до реального обновления и следующей проверки. Новые тексты
не подтверждаются заранее. Платформенная точка —
`eligibleReleaseSummaries(items): Promise<ReleaseNotice[]>` в
`frontend/src/lib/releaseSummaryPlatform.ts`; Android-перенос должен связать её
через существующий alias с фактическим установленным versionCode и пропускать
только `apk_version <= installedVersionCode`. Новую push-службу или bridge для
этого не создавать. Native-проверка отмечается в Android-отчёте после переноса.

## Контракт оверлея

- `GET /notifications/release-notices?expected_owner=USER_UUID` с текущим JWT
  возвращает страницу до 20 непрочитанных выжимок: `items` с `id`, `release_key`,
  `title`, `message_text`, `apk_version`, `apk_url`, `created_at`. Канал внешней доставки не
  ограничивает доступ к собственной выжимке; чтение GET не подтверждает.
  Обязательное nullable `next_cursor` содержит UUID последнего элемента, когда
  есть ещё страницы. Передавать его как `cursor=UUID`; стабильный порядок —
  `created_at DESC, id DESC`. Якорь должен принадлежать этому получателю; уже
  прочитанный якорь остаётся допустимым. Чужой/отсутствующий даёт одинаковый404.
  Клиент загружает все страницы, проверяет продвижение курсора и исключает
  повторные ID. Если часть не загрузилась, показанная часть и действие повторной
  загрузки явно видимы; закрытие не подтверждает ещё не показанные записи.
- `POST /notifications/release-notices/NOTICE_UUID/seen?expected_owner=USER_UUID`
  с тем же JWT идемпотентно отмечает прочтение только этого аккаунта. Ожидаемый
  owner обязателен: несовпадение с JWT даёт 409 до чтения/изменения receipts,
  в том числе при смене защищённой нативной сессии во время запроса.
- Закрытие сразу скрывает оверлей. До подтверждения сервера сохраняется только
  список всех показанных UUID для этого аккаунта без вытеснения после64 записей;
  запись пакетная, guard сырых данных — 1МиБ. При запрете/квоте локального
  хранилища все ID остаются в памяти текущего сеанса; после восстановления
  сети или следующего открытия повторяется только идемпотентная отметка чтения.
  Отправка ACK — последовательно, одна попытка на ID за событие; она не блокирует
  независимую загрузку новых выжимок даже при удержанном старом запросе.
  Ошибки503/409/сети сохраняют intent; окончательный404 текущего owner убирает
  только pending ACK, сохраняя закрытие в этом сеансе.
  Текст, credentials и дневник в этот список не записываются. Если браузер
  запрещает запись локального хранилища, закрытие сохраняется в текущем сеансе.

Это механизм анонса выпуска. Напоминания о тренировке, добавках и другие
существующие каналы/расписания используют свои прежние контракты.
