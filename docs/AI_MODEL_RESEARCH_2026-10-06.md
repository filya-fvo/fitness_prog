## Решение

При ограничении **только текущий VPS, без увеличения ресурсов** основной кандидат для замены текстового Qwen2.5-3B — **Qwen3.5-2B, GGUF Q4_K_M, без thinking и без загрузки vision encoder**. Резерв для сравнительного теста — **Qwen3-1.7B Q4_K_M**, также без thinking.

Для этикеток необходим отдельный выбор OCR и исправление разбора таблиц. Основной кандидат нового OCR — **PP-OCRv5_mobile_det + cyrillic_PP-OCRv5_mobile_rec в ONNX Runtime**, после ограниченного испытания памяти и точности. Tesseract `rus+eng` остаётся контрольным вариантом и резервом. Полный PaddleOCR runtime нельзя заранее считать подходящим для этого сервера.

**Qolda не рекомендована основной заменой на этом VPS:** расход памяти её языковой части и обработки изображений оставляет слишком мало запаса всему приложению; точность на русских пищевых этикетках не подтверждена опубликованными тестами.

Это выбор кандидатов по источникам, архитектуре и ограничениям, а не результат соревнования моделей на VPS. Новые веса не скачивались, inference не запускался, к VPS не подключались, production не изменялся. Исследование выполнено основным агентом и тремя независимыми агентами: текстовые модели, OCR/vision и текущая интеграция.

## 1. Что сейчас ограничивает качество

### Конфигурация

- Документированный VPS: **2 vCPU / 4 ГБ RAM / 50 ГБ NVMe**. Это характеристики из `docs/TIMEWEB_DOMAIN_CUTOVER.md:23`, не свежий замер сервера.
- В `docker-compose.yml:122` закреплены llama.cpp Docker image по digest, файл `qwen2.5-3b-instruct-q4_k_m.gguf` и alias модели. Изменение только `LLM_MODEL` не заменит веса.
- LLM получает максимум `2800m` памяти, два CPU-потока, контекст 4096 токенов и один слот. Остальную память используют PostgreSQL, API, Redis, worker, OCR, frontend и системные процессы.
- OCR ограничен `384m`; используется отдельный Tesseract subprocess.
- Внешние AI API запрещены правилами проекта и отклоняются клиентом. Рекомендация сохраняет полностью локальную обработку.

### Подтверждённые проблемы интеграции

| Ограничение | Доказательство | Следствие |
|---|---|---|
| Ответ тренера ограничен 64 токенами | `backend/app/services/ai_engine.py:194–207` | Содержательный ответ может закончиться до завершения мысли. Настройки 320 токенов / 75 секунд не отменяют явные 64 / 35 в этом вызове. |
| Prompt требует 180–350 знаков | `backend/app/ai/prompts.py:12` | Короткий ответ задан продуктом независимо от силы модели. |
| Контекст приложения 700 символов, каталог 250, история 250, вопрос 600 | `backend/app/services/ai_engine.py:250–283` | Нужные факты могут быть удалены до inference. |
| История содержит только две записи | `backend/app/services/ai_engine.py:356–360` | Модель не помнит предыдущие обсуждения, которых нет во входе. |
| Маркер боли содержит подстроку `боле` | `backend/app/services/ai_engine.py:74–116` | «Как сделать тренировку более эффективной?» получает правило о боли вместо вызова модели. |
| Есть фильтр только русского ответа | `backend/app/services/ai_engine.py:215` | Английский ответ и даже русский ответ со словом `deadlift` отклоняются. Поддержка RU/EN моделью сама по себе не даёт приложению двуязычный режим. |
| Ожидание свободной модели только одна секунда | `backend/app/services/local_llm.py:67` | Следующий пользователь быстро получает fallback при занятости модели. |
| Клиент не проверяет `finish_reason` | `backend/app/services/local_llm.py:93` | Ответ, обрезанный лимитом токенов, может считаться успешным. |

Маршрутизация вопроса с «более» и отклонение английских ответов проверены локально: функции извлечены из актуального Python-файла через AST и выполнены изолированно, без запуска API, БД и модели. Получены `rule_only=True`, ответ о боли для обычного вопроса и отклонение обоих английских примеров. Это воспроизведение функций, не end-to-end проверка production.

Эти ограничения объясняют часть плохого поведения, но не доказывают причину каждого пользовательского случая. Для этого нужны исходные вопросы, результаты и причины fallback. При замене следует отдельно учитывать timeout, занятость, правило безопасности, отклонение вывода и качество самой модели.

### Почему первым выбран Qwen3.5-2B

Русский и английский входят в официальный список языков семейства. [Список Qwen3.5](https://qwen.ai/blog?id=qwen3.5).

Модель имеет Apache-2.0 лицензию и по умолчанию работает без thinking. Авторская таблица показывает преимущество над Qwen3-1.7B в некоторых задачах знаний, но снижение в IFEval: новую модель нельзя считать лучшей по всем критериям. Автор также предупреждает о возможных циклах рассуждения при включённом thinking. [Официальная карточка Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B).

Большой заявленный контекст модели не следует использовать целиком на VPS. Стартовая конфигурация испытания: **2048 токенов контекста, один слот, два потока**, затем 4096 при подтверждённом запасе. Для полезного ответа тренера проверить бюджет 192–256 токенов и завершение ответа; это предлагаемые значения, а не измеренный оптимум.

Для текстовых запросов vision projector загружать не требуется. В выбранной сборке он отдельно занимает 668 МБ. Возможность отключения мультимодальной части описана в [документации llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md).

Текущий Docker image закреплён по digest: до перехода проверить поддержку архитектуры, chat template и отключения thinking именно в используемой сборке. При необходимости обновить llama.cpp до проверенной закреплённой версии. Нельзя предполагать, что старый образ поддерживает новую модель.

### Оценка Qolda

Qolda действительно существует: ISSAI / Nazarbayev University, 4,3 млрд параметров, Qwen3-4B плюс InternViT-300M, русский/английский/казахский, Apache-2.0. Официальные результаты включают русский текст, но OCRBench представлен для английского и казахского; это не проверка русских пищевых этикеток. [Карточка Qolda](https://huggingface.co/issai/Qolda).

Официальный Q4_K_M составляет **2,32 GiB, около 2,50 ГБ**, причём таблицы относятся к языковой части; vision тестируется отдельно. Опубликованные скорости A100, Mac и Snapdragon не переносятся на два x86 vCPU. [Qolda GGUF](https://huggingface.co/issai/Qolda_GGUF).

Новая Qolda-AVL-5B использует дополнительно примерно 0,8 ГБ для vision-only либо 2,2 ГБ для audio+vision; аудио требует патча llama.cpp. [Qolda-AVL GGUF](https://huggingface.co/issai/Qolda-AVL-5B-GGUF).

На сервере с 4 ГБ для всех сервисов обещание «Qolda хватит памяти» необоснованно. При коротком контексте можно исследовать текстовую часть, но для основной замены она менее практична, чем выбранные 2B/1.7B кандидаты.

## 3. Этикетки: почему замена тренера не решит задачу

По актуальному коду путь такой:

```text
Фото → Tesseract rus+eng → текст → детерминированный parser → редактируемый черновик
```

**LLM в этом пути вообще не вызывается:** `backend/app/services/nutrition_label_vision.py:191–193`. Руководство `ADMIN_AI_MODEL_RUNBOOK.md` ещё описывает передачу OCR-текста Qwen; его следует синхронизировать при реализации.

Дополнительная проблема: `ocr_main.py` извлекает текст из TSV, но теряет координаты слов. `_line_value` берёт первое число после имени нутриента. На таблице «на 100 г / на порцию / % нормы» можно получить неправильную колонку даже при правильном чтении цифр.

### Предлагаемый порядок улучшения

1. Подготовить набор настоящих русских и английских этикеток с вручную проверенными числами и основой расчёта.
2. Сохранить координаты строк и колонок; явно выбирать «100 г/мл» или порцию, учитывать ккал/кДж и десятичную запятую. Не восстанавливать невидимые числа догадками.
3. Проверить улучшения Tesseract: крупная область таблицы, выравнивание и несколько подходящих режимов сегментации. Нынешний `--psm 6` предполагает единый блок текста; одна настройка не подходит всем упаковкам.
4. Сравнить с **PP-OCRv5_mobile_det + cyrillic_PP-OCRv5_mobile_rec** через ONNX Runtime, одним заданием, с небольшим batch и без дополнительных моделей layout/orientation/unwarping.
5. Оставить результат редактируемым; сомнительные и отсутствующие поля оставлять пустыми. Общая уверенность OCR не гарантирует правильности конкретной цифры.

Кириллический recognizer официально поддерживает **русский и английский**. Это позволяет проверить одну модель для смешанных этикеток. Не выбирать автоматически новейший PP-OCRv6 без проверки русского языка. [Таблица языков PP-OCRv5](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.en.md).

Официальные файлы ONNX: [detector](https://huggingface.co/PaddlePaddle/PP-OCRv5_mobile_det_onnx), [Cyrillic recognizer](https://huggingface.co/PaddlePaddle/cyrillic_PP-OCRv5_mobile_rec_onnx). Нужно согласовать предобработку, декодирование и словарь с конкретной моделью; одного скачивания файла недостаточно.

**Маленькие веса OCR не означают маленький runtime.** В официальном CPU-тесте обычный PP-OCRv5 mobile показал около 2,22 ГБ пикового RAM. Это другая конфигурация, не прогноз памяти выбранного Cyrillic ONNX worker. Но полный Paddle runtime нельзя устанавливать, исходя лишь из нескольких мегабайт весов. [Ресурсный benchmark PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5.md).

Завершение OCR worker после обработки уменьшит память в простое, но не уберёт пик одновременно с LLM. Перед вводом проверить совместное потребление; при нехватке памяти ограничивать совместный запуск либо выгружать модель. Swap не делает inference быстрым.

Как дополнительный эксперимент возможна обработка фото той же Qwen3.5-2B с vision encoder вместо второй большой VLM. Однако дополнительная память, время анализа изображения и точность цифр не измерены. Это не основной путь для первого выпуска на 4 ГБ.

## 4. Как принять решение по результатам испытания

Модель-кандидат выбрана, но production переключать только после сравнительного теста. Нынешние unit-тесты подменяют модель или проверяют правила, а не качество реального inference.

### Текст: три контрольных конфигурации

1. Нынешняя Qwen2.5-3B с исправленной маршрутизацией и достаточным бюджетом ответа — контроль влияния интеграции.
2. Qwen3.5-2B Q4_K_M в тех же условиях.
3. Qwen3-1.7B Q4_K_M в тех же условиях.

Для чистого сравнения передавать одинаковые факты и задания. Отдельно проверять полный путь приложения. Оценить 30–50 вопросов: русский/английский ввод, техника, выбор из каталога, личная динамика, недостаток данных, уточнения предыдущего вопроса, числа и обычные формулировки со словами «более», «вес», «тренировка».

Измерять полезность, соблюдение каталога, полноту ответа, выдуманные факты, неправильные fallback, cold/warm latency, p50/p95, пиковую память и поведение двух одновременно обратившихся пользователей. Английский вывод проверять только если двуязычный режим приложения действительно входит в требование; сейчас интерфейс намеренно требует русский.

Предлагаемые критерии допуска: нет OOM, нет постоянного swap pressure, есть запас порядка 500 МБ доступной памяти при совместной нагрузке; обычный ответ укладывается в существующий бюджет до 35 секунд; ответы завершаются; в контрольном наборе нет выдуманных пользовательских фактов и опасных советов. Это критерии для будущего измерения, не обещание достигнутых результатов.

### Этикетки: отдельный тест

30–50 реальных фото: русский/английский/смешанный текст, блики, мелкий шрифт, изогнутая упаковка, две колонки, порции, кДж/ккал. Считать правильность каждого числового поля и основы расчёта, ложное заполнение, пропуски, память и задержку. Общие OCRBench и оценки чтения документов не заменяют этот набор.

Сравнивать исходный Tesseract, улучшенный Tesseract и Cyrillic ONNX OCR; для каждого отдельно проверить один и тот же parser. При отсутствии измеренного преимущества не усложнять production новым runtime.

## 5. Что входит в последующую реализацию

- Исправление ложных срабатываний маршрутизации; проверка отличия общего вопроса от анализа личных данных.
- Согласованный бюджет ответа и структурированный релевантный контекст вместо обрезки произвольного текста.
- Причины fallback и проверка завершения ответа; сохранение защиты от утечки reasoning.
- Закреплённые веса, контрольная сумма и проверенная версия llama.cpp.
- Координаты OCR, корректный выбор колонок и контроль числовых полей.
- Регрессионные тесты, реальная оценка моделей, обновление runbook и документации.
- Отдельный production-выпуск по правилам AGENTS.md после зелёных проверок и с возможностью возврата к прежним весам.

На этапе этого исследования перечисленные изменения не выполнялись. Фактическое преимущество новой модели, её RAM и скорость на VPS остаются предметом испытания.

## 6. Первые реальные примеры от владельца

После исследования владелец предоставил шесть домашних фото этикеток.
Оригиналы и визуально проверенный эталон сохранены в
`backend/tests/fixtures/nutrition_labels_20261006/`; диагностический runner
и результаты — в `artifacts/nutrition-label-benchmark-20261006/`.

Проверка текущего parser на вручную прочитанных фрагментах дала 21/21
правильных явных числовых полей, но три расхождения: не распознана основа
«100 г» на двух этикетках без предлога, а сахароза записана как сумма всех
сахаров. Полностью совпали 3/6 фрагментов. Значение углеводов десерта со
средней уверенностью исключено из строгой оценки.

Это проверка разбора текста, не OCR. Реальное распознавание фотографий и
новые модели не запускались: в доступной локальной среде нет Tesseract и
работающего OCR-сервиса. Данный набор подтверждает необходимость отдельно
исправлять parser, но не доказывает преимущество какой-либо модели.
