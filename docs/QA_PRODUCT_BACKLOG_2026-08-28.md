## 1. Объём и методика

Под словом «тяжёлый» в запросе владельца принят существующий уровень
`advanced` — «Продвинутый». Проверено 18 базовых персон:

- пол: женщина / мужчина;
- уровень: новичок / опытный / продвинутый;
- место: зал / дом / улица.

Для каждой персоны подбор дополнительно прогнан с тремя целями:
`maintain`, `lose_fat`, `gain_muscle`. Итого проверено 54 результата
ранжирования. Инвентарь задавался реалистично:

- зал: штанга, гантели, тренажёры, собственный вес;
- дом: собственный вес, гантели, резинки;
- улица: собственный вес и турник.

Проверка состояла из четырёх уровней:

1. Фактический seed из `backend/scripts/seed_content/programs.json` и реальный
   алгоритм `frontend/src/utils/programRecommend.ts`.
2. Контракты замеров, аналитики и ИИ по frontend/backend коду и unit-тестам.
3. Полный текущий административный путь по API, UI и Playwright-сценариям.
4. Проектирование соревнований, приглашений и входа через Telegram по
   актуальной официальной документации Telegram.

Не выполнялись изменения реальных пользовательских данных, массовые сообщения и
реальные соревнования на длительном временном отрезке. Отправка Telegram, жесты
на физическом устройстве и поведение локального Qwen под длительной нагрузкой
остаются отдельным ручным QA; автоматические моки этого не доказывают.

Исторические причины из первоначального аудита закрыты в `AI-P1-01..03`.
Маршрутизация и период определяются на backend, исходный вопрос участвует в
prompt, а нагрузка использует общую нормализацию `per_hand × 2`. Подходы без
веса и работа по времени остаются отдельными показателями и не подмешиваются в
килограммы. Открытым остаётся ручной длительный тест локального Qwen: unit-тесты
проверяют контракты и очистку, но не качество каждого свободного ответа модели.

Backend проверяет реальные права администратора; frontend-проверка username нужна
только для сокрытия UI и не является границей безопасности. Опасные операции
аудируются и имеют подтверждения. Автоматические E2E используют API-моки, поэтому
реальную доставку Telegram они не доказывают.

Первоначальные P1-наблюдения о пустых публичных программах и неуправляемой
рассылке закрыты. Сервер не публикует невалидный draft, активные пользователи
сохраняют закреплённую версию, а запланированную рассылку можно отменить до
начала. Подтверждённое оставшееся отклонение — архитектура UI программ: её нужно
вынести из legacy-страницы до дальнейшего расширения Admin 6.

## 7. Концепция соревнований

### Принципы

- Только добровольное участие (`opt-in`) и понятный выход.
- В глобальном рейтинге — псевдоним и агрегированный балл. Вес, талия, фото,
  email, Telegram ID и абсолютные обхваты не публикуются.
- Не сравнивать абсолютный тоннаж, вес тела или число тренировок между людьми с
  разным полом, уровнем, программой и доступным инвентарём.
- Не награждать «минимум калорий», максимальную скорость похудения, боль,
  тренировки без отдыха или опасное увеличение веса.
- Минимальный размер публичной когорты, рекомендуемо 20 участников; иначе
  показывать личный процентиль без списка людей.
- Все баллы воспроизводимы сервером из неизменяемых фактов; ручные записи можно
  учитывать с меньшим доверием и пометкой.

### Варианты глобальных соревнований

Статус первого варианта: **регулярность реализована 1 сентября 2026 года**.
Добавлен добровольный 28-дневный сезон с неизменяемым снимком личного расписания,
случайным псевдонимом, группами 1–2/3/4+ дня и серверной формулой adherence.
Публичный список скрыт до 20 рейтинговых участников одной группы; поздний вход
даёт личный результат, но не место. Выход исключает пользователя до следующего
сезона. API не возвращает логин, Telegram ID, вес, обхваты или дневник.

1. **Регулярность:** доля выполненных плановых тренировок, а не сырое количество.
2. **Серия недель:** недели, в которых закрыта персональная цель 2/3/4 дня.
3. **Силовой прогресс:** процент изменения расчётного 1ПМ в одном и том же
   упражнении, оборудовании и диапазоне 1–12 повторов.
4. **Прогресс цели:** приватно вычисляемый процент изменения талии/веса к своей
   цели; наружу выходит только балл и место.
5. **Сбалансированная неделя:** тренировки + заполненность восстановления и
   питания, без поощрения дефицита сна или калорий.
6. **Командный сезон:** сумма нормализованных баллов, где вклад одного участника
   ограничен, чтобы команда не зависела от одного лидера.

Рекомендуемый старт — отдельные рейтинги «Регулярность» и «Силовой прогресс», а
не один непрозрачный общий балл.

Пример прозрачных формул:

```text
adherence = 100 × completed_planned / eligible_planned, cap 100
consistency = 100 × active_weeks / season_weeks
strength_delta = 100 × (latest_e1rm - baseline_e1rm) / baseline_e1rm
measurement_delta = 100 × goal_direction × (latest - baseline) / baseline
```

Для силы использовать медиану нескольких валидных подходов и ограничение
аномального скачка. Для замеров baseline/latest строить по двум близким точкам,
если они есть, чтобы одна ошибка рулетки не решала сезон.

### Соревнование с другом

Статус расширенного варианта: **реализован 2 сентября 2026 года**. Доступен
произвольный срок 7–365 дней и до четырёх факторов: adherence, снижение веса,
уменьшение талии и относительный e1RM выбранного упражнения. Baseline фиксируется
после согласия обоих, абсолютные данные второго участника не раскрываются, а
общий исход считается по победам в отдельных факторах без смешивания разных
процентных шкал.

Поток:

1. Пользователи сначала устанавливают дружбу безопасной ссылкой или ручным кодом.
2. Создатель выбирает друга, срок 7–365 дней, название и до четырёх факторов.
3. Друг видит отдельное предложение соревнования, правила и требуемые исходные
   данные; переход по обычной странице не является согласием.
4. При явном принятии повторно проверяются оба участника и фиксируются baseline,
   расписания и timezone. До этого соревнование остаётся `pending`.
5. Во время соревнования каждый видит собственные абсолютные данные и только
   агрегированные проценты друга. Каждый может выйти, удалить дружбу или
   заблокировать пользователя.

Если цели или программы различаются, предлагать нейтральные метрики
«регулярность/серия», а не абсолютный вес и тоннаж.

### Модель данных

Фактическая модель после migrations 33–37:

- `friendships`: упорядоченная пара user IDs, status
  `accepted|removed|blocked`, initiator, timestamps, unique pair;
- `invites`: `token_hash`, короткий `code_hash`, inviter, purpose
  `referral|referral_social|friend|challenge`, expiry, max/use count, revoked_at;
- `invite_redemptions`: invite, user, этап `opened|registered|accepted`, unique;
- `competitions`: частное соревнование, `pending|active|finished|cancelled`,
  срок, factors, версия приватности и алгоритма;
- `competition_participants`: competition/user, consent, снимок расписания,
  timezone, baseline и joined/left timestamps;
- `global_competition_seasons` и `global_competition_participants`: отдельный
  добровольный сезон регулярности, псевдоним, когорта и снимок расписания;
- `referral_attributions`: отдельная от friendship запись источника регистрации.

Отдельная `competition_scores` пока не нужна: текущие ограниченные выборки
пересчитываются сервером детерминированно при чтении. При росте данных следует
добавить версионированный кэш/worker без изменения исходных фактов.

Реферал, дружба и участие в соревновании — три разных согласия. Переход по ссылке
не должен автоматически добавлять друга или участника.

### API и защита

Фактические endpoints:

- `POST /invites`, `POST /invites/preview`, `POST /invites/accept`,
  `POST /invites/{id}/revoke`; credential передаётся в JSON body, а не в URL;
- `GET /friends`, `POST /friends/{id}/{remove|block}`;
- `GET /competitions`, `POST /competitions/friend`,
  `POST /competitions/{id}/{accept|leave}`;
- `GET /competitions/global/current` и
  `POST /competitions/global/current/{join|leave}`.

Административное управление глобальными сезонами и агрегированная модерация без
раскрытия замеров остаются отдельной будущей доработкой.

Токен приглашения: минимум 128 бит случайности, base64url, в БД только hash,
срок и лимит использований. Короткий ручной код — отдельный случайный код с
rate limit. Нельзя помещать user ID, вес или цель в URL. Все операции
идемпотентны; списки фильтруются по видимости и блокировкам.

Acceptance criteria MVP:

- два тестовых пользователя связываются ссылкой и кодом, оба подтверждают;
- повторное открытие не создаёт дубль;
- истёкший/отозванный/подобранный код безопасно отклоняется;
- блокировка немедленно скрывает связь и будущие приглашения;
- глобальный endpoint не возвращает персональные замеры;
- score одинаков для sync/offline повторов и содержит `algorithm_version`;
- тесты покрывают race двух accept, self-invite, replay и удалённого пользователя.

## 8. Приглашение друга из приложения

Статус foundation и dual-mode: **реализовано 31 августа — 1 сентября 2026
года**. Добавлены безопасные
многоразовые приглашения на 14 дней, Telegram `startapp`, browser/PWA-ссылка,
официальный Telegram Share, Web Share/copy fallback и ручной код. В базе остаются
только HMAC-хэши токена и кода; подбор короткого кода ограничен 30 попытками в час
на авторизованного пользователя. Preview и принятие требуют действующей app-сессии,
собственное, истёкшее и отозванное приглашение отклоняются, повторное принятие
идемпотентно. Для аккаунта, созданного после открытия приглашения, принятие
сохраняет только referral attribution. Если оба аккаунта уже существовали, то же
явное принятие создаёт дружбу и предложение/старт частного соревнования на
регулярность. Эти режимы определяются сервером; простой переход по ссылке ничего
не принимает.

Рекомендуемый формат основной ссылки:

```text
https://t.me/<BOT_USERNAME>?startapp=i_<opaque-token>
```

Официальная документация Telegram передаёт `startapp` в `start_param` и
`tgWebAppStartParam`: [Telegram Mini Apps](https://core.telegram.org/bots/webapps).
Для старых/ботовых сценариев поддержать
`https://t.me/<BOT_USERNAME>?start=i_<opaque-token>`; Bot deep link принимает
до 64 base64url-символов: [Telegram Bot Features](https://core.telegram.org/bots/features#deep-linking).

Поток клиента:

1. Прочитать start parameter только как недоверенную подсказку.
2. Сначала завершить обычную проверку Telegram `initData` и получить JWT.
3. Затем запросить server preview приглашения.
4. Показать экран подтверждения; не принимать приглашение автоматически.
5. Для браузера/PWA дать поле ручного кода.

Кнопка «Пригласить друга» внутри Mini App открывает официальный share URL
`https://t.me/share/url?url=...&text=...` через `openTelegramLink`. Telegram
покажет выбор чата, а пользователь сможет изменить текст: [Sharing Button](https://core.telegram.org/widgets/share).
В обычном браузере использовать Web Share API, затем fallback «Скопировать».

Отдельно считать события `created`, `shared`, `opened`, `registered`, `accepted`.
Не считать успешным приглашением один клик.

## 9. Telegram Login для сайта

Статус: **реализовано 31 августа 2026 года** через актуальный официальный
JavaScript SDK и OIDC `id_token`; старый iframe Login Widget не используется:
[Log In With Telegram](https://core.telegram.org/bots/telegram-login).

Фактический поток:

1. В BotFather регистрируется точный Allowed URL сайта и алгоритм `RS256`.
2. `GET /auth/telegram/browser/config` возвращает публичный Client ID и подписанный
   короткоживущий nonce. Секрет бота в браузер не передаётся.
3. Официальный SDK запрашивает только scope `profile` и возвращает `id_token`
   callback-функции; токен не помещается в URL.
4. `POST /auth/telegram/browser` сверяет подпись по Telegram JWKS, `kid`, `alg`,
   `iss`, `aud`, `exp`, `iat` и nonce, затем находит пользователя по `telegram_id`.
5. Используется общий с Mini App upsert пользователя и существующий безопасный
   перенос локальных данных; отдельный Telegram-аккаунт в БД не создаётся.
6. JWKS ограничен по размеру и схеме, кэшируется и обновляется при ротации `kid`;
   токены и nonce не журналируются.

Телефон и право писать пользователю по умолчанию не запрашивать. Если позже они
понадобятся, это отдельное явно объяснённое согласие.

Покрыто тестами: валидная RSA-подпись, nonce mismatch/expiry/tampering, wrong
audience, новый и существующий Telegram user, API-контракт и browser E2E до
создания app-сессии. Реальный popup/cancel/retry проверяется вручную после
регистрации production URL в BotFather.
