## 1. Объём и методика

Под словом «тяжёлый» в запросе владельца принят существующий уровень
`advanced` — «Продвинутый». Проверено 18 базовых персон:

- пол: женщина / мужчина;
- уровень: новичок / опытный / продвинутый;
- место: зал / дом / улица.

Для каждой персоны подбор дополнительно прогнан с тремя целями:
`maintain`, `lose_fat`, `gain_muscle`. Итого проверено 54 результата
ранжирования. Инвентарь задавался реалистично:

- зал: штанга, гантели, тренажёры, собственный вес;
- дом: собственный вес, гантели, резинки;
- улица: собственный вес и турник.

Проверка состояла из четырёх уровней:

1. Фактический seed из `backend/scripts/seed_content/programs.json` и реальный
   алгоритм `frontend/src/utils/programRecommend.ts`.
2. Контракты замеров, аналитики и ИИ по frontend/backend коду и unit-тестам.
3. Полный текущий административный путь по API, UI и Playwright-сценариям.
4. Проектирование соревнований, приглашений и входа через Telegram по
   актуальной официальной документации Telegram.

Не выполнялись изменения реальных пользовательских данных, массовые сообщения и
реальные соревнования на длительном временном отрезке. Отправка Telegram, жесты
на физическом устройстве и поведение локального Qwen под длительной нагрузкой
остаются отдельным ручным QA; автоматические моки этого не доказывают.

## 3. Замеры и аналитика

### Проверенные сценарии

| Сценарий | Результат |
|---|---|
| Первый частичный замер | Работает; можно заполнить только измеренные поля |
| Повторный замер и график | Работает после двух точек, выводится до 12 последних точек |
| Историческая запись | Работает; профиль сохраняет вес из последней по дате записи с весом |
| Запись только обхватов после записи веса | Работает; текущий вес не теряется |
| Сводка в «Прогрессе» | Показывает последнюю запись и дельту к предыдущей записи |
| Offline | История и сохранение замеров недоступны, durable offline queue отсутствует |

### Проблемы

- Дельта поля считается к предыдущей **записи**, а не к предыдущему ненулевому
  значению этого же поля. Если вчера сохранена только талия, сравнение груди с
  более ранним замером исчезает.
- Аналитика не учитывает цель. `−2 см` для талии и `+2 см` для бицепса показаны
  как числа без пояснения; знак сам по себе не означает успех.
- Нет выбора периода, базовой точки, цели на графике и нормализации по числу
  дней между нерегулярными замерами.
- Нельзя удалить ошибочную запись целиком из UI; можно только переписать поля.
- Страница «Прогресс» загружает до десяти лет сырых замеров на клиент. До
  появления больших объёмов это работает, но для долгосрочного продукта нужны
  серверные агрегаты/пагинация.
- ИИ не получает историю замеров, поэтому пользователь не может получить
  доказательный текстовый разбор этой аналитики.

## 4. ИИ-тренер: фактическое поведение

| Запрос пользователя | Фактический путь | Вывод |
|---|---|---|
| «Как идёт прогресс в жиме?» | chat + последние 3 тренировки | Может ответить, если нужное упражнение попало в три записи |
| «Проанализируй мой прогресс за месяц» | analyze, всегда 14 дней из текущего UI | Текст «за месяц» не меняет период; отчёт только о тренировках |
| «Проанализируй снижение веса» | analyze | Ошибочно получает отчёт о тренировках без динамики веса |
| «Как изменилась талия?» | chat | В контексте есть только текущий вес, истории обхватов нет |
| «Как было питание за неделю?» | chat | Дневник питания и фактические калории в контекст не входят |
| «Что есть после тренировки?» | безопасное rule-based правило | Работает, ответ намеренно общий без выдуманных порций |
| «Болит плечо/колено» | безопасное rule-based правило | Модель не вызывается, есть остановка нагрузки и медицинский дисклеймер |
| «Разбор недели: объём и восстановление» | analyze | Сон, шаги и восстановление не учитываются |

Подтверждённые причины находятся в `frontend/src/features/ai-chat/pages/Chat.tsx`,
`backend/app/ai/context.py` и `backend/app/services/ai_engine.py`:

- любой текст с `прогресс`, `проанализ` или `разбор ... недели` переключается на
  единый workout-анализ;
- поле `message` сохраняется в историю, но не участвует в построении отчёта;
- контекст чата содержит профиль, активную программу и только три последние
  тренировки; питания, замеров и daily metrics там нет;
- backend-объём считает `weight × reps`, но не удваивает `per_hand`, хотя
  frontend делает это. Поэтому один и тот же подход с двумя гантелями имеет
  разные объёмы в интерфейсе и ИИ;
- подходы со своим весом и упражнения по времени дают нулевой тоннаж. Сравнивать
  пользователей или даже разные типы тренировок по одному тоннажу нельзя.

## 5. Аудит административного пути

| Раздел | Что проверено | Что неудобно или отсутствует |
|---|---|---|
| Состояние системы | loading/error/retry, API/DB/Redis/worker/backup | Нет истории состояния, автообновления и перехода к связанной диагностике |
| Журнал | серверные фильтры, пагинация, снимки до/после, correlation ID | Нет поиска по объекту/пользователю, экспорта и прямой ссылки из карточки объекта |
| Пользователи | поиск, карточка, тренировки, связь, сообщения, настройки, экспорт, очистка, архив | Два блока надо загружать вручную; нет email/Web Push fallback для browser-only пользователя |
| Рассылки | черновик, аудитория, тест себе, двойное подтверждение, расписание, retry | Нет отмены запланированной рассылки, явного часового пояса и расшифровки причин ошибок |
| Упражнения | поиск, фильтры, create/update, preflight медиа, дубли, блокировка архивации | Нет восстановления из архива, предупреждения о несохранённых данных и применения проверенного JSON-пакета |
| Программы | простое create/update/archive | Текущая форма создаёт публичный шаблон с `schedule: []`; начать такую программу нельзя |

Backend проверяет реальные права администратора; frontend-проверка username нужна
только для сокрытия UI и не является границей безопасности. Опасные операции
аудируются и имеют подтверждения. Автоматические E2E используют API-моки, поэтому
реальную доставку Telegram они не доказывают.

Особо важные наблюдения:

1. Текущая кнопка «Добавить программу» создаёт `is_template=true` с пустым
   расписанием. Сервер принимает запись, каталог показывает её пользователям, а
   старт завершается `400 «В программе нет тренировочных дней»`.
2. `is_template` не является статусом публикации. Нет состояний «черновик» и
   «опубликовано», версий и безопасной привязки активных пользователей к старой
   версии.
3. У рассылки есть enum `cancelled`, но нет API/UI отмены. Временная ошибка
   preview-аудитории также не очищается после успешного повторного расчёта, а
   конкурирующие debounce-запросы могут кратко показать устаревшее число.
4. Карточка пользователя хорошо разделяет тяжёлые блоки, но администратор не
   понимает, что перед переключением напоминаний обязательно надо вручную
   загрузить «Связь и уведомления».

Отмена, как и запуск, фиксируется в immutable audit.

### `ADM-P1-03` — безопасный smoke реальной связи

**Реализован в 0.20.42; реальный write-smoke выполняется только после настройки
выделенного тестового Telegram ID.**

Создать отдельного тестового Telegram-получателя и read/write smoke с явным
флагом, который отправляет только этому ID: личное сообщение, guide и тест

### `ADM-P2-01` — уменьшить трение карточки пользователя

### `ADM-P2-02` — завершить жизненный цикл упражнений

Предупреждать об уходе с несохранённой формы, дать список архива и безопасное

## 7. Концепция соревнований

### Принципы

- Только добровольное участие (`opt-in`) и понятный выход.
- В глобальном рейтинге — псевдоним и агрегированный балл. Вес, талия, фото,
  email, Telegram ID и абсолютные обхваты не публикуются.
- Не сравнивать абсолютный тоннаж, вес тела или число тренировок между людьми с
  разным полом, уровнем, программой и доступным инвентарём.
- Не награждать «минимум калорий», максимальную скорость похудения, боль,
  тренировки без отдыха или опасное увеличение веса.
- Минимальный размер публичной когорты, рекомендуемо 20 участников; иначе
  показывать личный процентиль без списка людей.
- Все баллы воспроизводимы сервером из неизменяемых фактов; ручные записи можно
  учитывать с меньшим доверием и пометкой.

### Варианты глобальных соревнований

1. **Регулярность:** доля выполненных плановых тренировок, а не сырое количество.
2. **Серия недель:** недели, в которых закрыта персональная цель 2/3/4 дня.
3. **Силовой прогресс:** процент изменения расчётного 1ПМ в одном и том же
   упражнении, оборудовании и диапазоне 1–12 повторов.
4. **Прогресс цели:** приватно вычисляемый процент изменения талии/веса к своей
   цели; наружу выходит только балл и место.
5. **Сбалансированная неделя:** тренировки + заполненность восстановления и
   питания, без поощрения дефицита сна или калорий.
6. **Командный сезон:** сумма нормализованных баллов, где вклад одного участника
   ограничен, чтобы команда не зависела от одного лидера.

Рекомендуемый старт — отдельные рейтинги «Регулярность» и «Силовой прогресс», а
не один непрозрачный общий балл.

Пример прозрачных формул:

```text
adherence = 100 × completed_planned / eligible_planned, cap 100
consistency = 100 × active_weeks / season_weeks
strength_delta = 100 × (latest_e1rm - baseline_e1rm) / baseline_e1rm
measurement_delta = 100 × goal_direction × (latest - baseline) / baseline
```

Для силы использовать медиану нескольких валидных подходов и ограничение
аномального скачка. Для замеров baseline/latest строить по двум близким точкам,
если они есть, чтобы одна ошибка рулетки не решала сезон.

### Соревнование с другом

Поток:

1. Создатель выбирает 14/28 дней, один набор метрик и уровень раскрытия данных.
2. Приложение создаёт непрозрачное приглашение и код.
3. Друг открывает ссылку или вводит код, видит псевдоним пригласившего, правила,
   даты и какие данные будут сравниваться.
4. Только после явного согласия создаётся связь и фиксируются baseline обоих.
5. Во время соревнования показываются баллы, разница и события без скрытых
   обхватов/веса. Каждый может выйти, отключить связь, заблокировать или сообщить
   о злоупотреблении.

Если цели или программы различаются, предлагать нейтральные метрики
«регулярность/серия», а не абсолютный вес и тоннаж.

### Модель данных

Новые таблицы — только append-only migration:

- `social_profiles`: `user_id`, публичный alias, avatar preset,
  discoverability, visibility settings;
- `friendships`: упорядоченная пара user IDs, status
  `pending|accepted|blocked`, initiator, timestamps, unique pair;
- `invites`: `token_hash`, короткий `code_hash`, inviter, purpose
  `referral|friend|challenge`, payload, expiry, max/use count, revoked_at;
- `invite_redemptions`: invite, user, этап `opened|registered|accepted`, unique;
- `competitions`: kind `global|friend`, metric set, status
  `draft|open|active|finalizing|finished|cancelled`, dates, cohort rules;
- `competition_participants`: competition/user, consent snapshot, baseline,
  joined/left timestamps, unique;
- `competition_scores`: score, public metrics JSON, computed_at, algorithm
  version; тяжёлые пересчёты выполняет worker;
- `referral_attributions`: отдельная от friendship запись источника регистрации.

Реферал, дружба и участие в соревновании — три разных согласия. Переход по ссылке
не должен автоматически добавлять друга или участника.

### API и защита

Минимальные endpoints:

- `POST /invites`, `GET /invites/{token}/preview`,
  `POST /invites/{token}/accept`, `POST /invites/{id}/revoke`;
- `GET /friends`, `POST /friends/{id}/accept|block|remove`;
- `GET /competitions`, `POST /competitions/friend`,
  `POST /competitions/{id}/join|leave`, `GET /competitions/{id}/leaderboard`;
- admin: управление сезоном и агрегированная модерация без раскрытия замеров.

Токен приглашения: минимум 128 бит случайности, base64url, в БД только hash,
срок и лимит использований. Короткий ручной код — отдельный случайный код с
rate limit. Нельзя помещать user ID, вес или цель в URL. Все операции
идемпотентны; списки фильтруются по видимости и блокировкам.

Acceptance criteria MVP:

- два тестовых пользователя связываются ссылкой и кодом, оба подтверждают;
- повторное открытие не создаёт дубль;
- истёкший/отозванный/подобранный код безопасно отклоняется;
- блокировка немедленно скрывает связь и будущие приглашения;
- глобальный endpoint не возвращает персональные замеры;
- score одинаков для sync/offline повторов и содержит `algorithm_version`;
- тесты покрывают race двух accept, self-invite, replay и удалённого пользователя.

## 8. Приглашение друга из приложения

Рекомендуемый формат основной ссылки:

```text
https://t.me/<BOT_USERNAME>?startapp=i_<opaque-token>
```

Официальная документация Telegram передаёт `startapp` в `start_param` и
`tgWebAppStartParam`: [Telegram Mini Apps](https://core.telegram.org/bots/webapps).
Для старых/ботовых сценариев поддержать
`https://t.me/<BOT_USERNAME>?start=i_<opaque-token>`; Bot deep link принимает
до 64 base64url-символов: [Telegram Bot Features](https://core.telegram.org/bots/features#deep-linking).

Поток клиента:

1. Прочитать start parameter только как недоверенную подсказку.
2. Сначала завершить обычную проверку Telegram `initData` и получить JWT.
3. Затем запросить server preview приглашения.
4. Показать экран подтверждения; не принимать приглашение автоматически.
5. Для браузера/PWA дать поле ручного кода.

Кнопка «Пригласить друга» внутри Mini App открывает официальный share URL
`https://t.me/share/url?url=...&text=...` через `openTelegramLink`. Telegram
покажет выбор чата, а пользователь сможет изменить текст: [Sharing Button](https://core.telegram.org/widgets/share).
В обычном браузере использовать Web Share API, затем fallback «Скопировать».

Отдельно считать события `created`, `shared`, `opened`, `registered`, `accepted`.
Не считать успешным приглашением один клик.

## 9. Telegram Login для сайта

Использовать не старый iframe Login Widget, а актуальный **Log In With Telegram**
на базе Authorization Code Flow с PKCE/OIDC. Telegram прямо помечает старую
iframe-документацию как legacy: [Log In With Telegram](https://core.telegram.org/bots/telegram-login).

Рекомендуемый backend/BFF поток:

1. В BotFather зарегистрировать exact Allowed Origin сайта и exact callback URL,
   получить Client ID/Secret. Secret хранится только в production env.
2. `GET /auth/telegram-web/start`: создать `state`, `nonce`, PKCE verifier,
   сохранить одноразовое состояние в Redis на 10 минут и вернуть redirect.
3. `GET /auth/telegram-web/callback`: проверить state, обменять code сервером,
   проверить подпись ID token, `iss`, `aud`, `exp`, `iat`, `nonce` и Telegram
   subject.
4. Найти пользователя по `telegram_id`. При конфликте с email-only аккаунтом
   использовать существующий `account_merge`, не сливать данные молча.
5. Перенаправить в SPA с одноразовым коротким exchange code. Не помещать JWT,
   ID token или Telegram payload в URL/local logs.
6. SPA один раз обменивает code на текущую app-сессию; replay отклоняется.

Телефон и право писать пользователю по умолчанию не запрашивать. Если позже они
понадобятся, это отдельное явно объяснённое согласие.

Тесты: happy path, state/nonce mismatch, истёкший code, replay, wrong
issuer/audience, недоступный JWKS/token endpoint, новый пользователь, существующий
Telegram user, конфликт с email и merge choice, browser E2E cancel/retry.
