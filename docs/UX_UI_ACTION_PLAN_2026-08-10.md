# UX/UI-аудит и план улучшений

**Дата:** 2026-08-10  
**Статус:** реализация и автоматический QA завершены 2026-08-10; остаётся физический iOS/Android Telegram QA  
**Область:** пользовательские сценарии, мобильный и desktop UI, доступность, визуальная система

## 1. Контекст проверки

Проверены:

- мобильные экраны 393×852 и 320×568;
- desktop 1440×900;
- светлая и Telegram-подобная тёмная тема;
- новый пользователь и пользователь с заполненным профилем;
- главная, тренировки, программы, каталог, питание, прогресс, профиль, AI и «Ещё»;
- штатный запуск тренировки, разминка, GIF, массовая замена и перезагрузка страницы;
- прямое открытие активной тренировки без локальной IndexedDB-сессии;
- зоны нажатия, вертикальное и горизонтальное переполнение, базовая доступность.

Автоматические проверки на момент аудита:

- frontend unit: 53 теста пройдены;
- существующие Playwright E2E: 7 тестов пройдены;
- горизонтального переполнения на ширине 320 px не найдено;
- высота страницы программ на 320 px — около 5 800 px;
- высота каталога упражнений на 320 px — около 17 000 px.

Ограничение проверки: системные разрешения камеры, Telegram MainButton, haptic feedback и особенности реальных WebView необходимо дополнительно проверять на физических iOS/Android-устройствах внутри Telegram.

## 4. P0 — критичные пользовательские разрывы

### P0.1. Добавить браузерную кнопку в онбординг

**Статус: реализовано 2026-08-10.** Добавлена единая primary action, HTML-fallback вне Telegram, скрыта нижняя навигация онбординга, добавлена E2E-проверка перехода между шагами.

**Проблема**

Онбординг использует только Telegram MainButton. В обычном браузере после email-входа кнопки «Далее»/«Завершить» нет, поэтому новый пользователь не может пройти анкету.

**Причина в коде**

- `frontend/src/features/onboarding/pages/OnboardingPage.tsx`
- `frontend/src/features/workout/hooks/useMainButton.ts`

`useMainButton` ничего не отображает, если Telegram API отсутствует, а HTML-fallback в онбординге не предусмотрен.

**Шаги реализации**

1. Добавить в `useMainButton` признак доступности Telegram MainButton либо отдельный хук `useTelegramMainButtonAvailable`.
2. В `OnboardingPage` показывать закреплённую HTML-кнопку вне Telegram.
3. Использовать одну функцию действия для Telegram- и HTML-кнопки, чтобы логика шагов не расходилась.
4. Учесть `saving`, `generating` и `canNext` в disabled/loading состояниях.
5. Добавить нижний отступ с учётом safe area и нижней навигации либо скрыть навигацию во время онбординга.
6. Добавить E2E: email/browser → пройти все семь шагов → попасть на главную.

**Критерии готовности**

- Онбординг полностью проходится вне Telegram.
- В Telegram остаётся нативный MainButton без дублирующей HTML-кнопки.
- Повторный тап во время сохранения не создаёт два запроса.
- После завершения назначена программа и открыта главная.

### P0.2. Восстанавливать активную тренировку с сервера

**Статус: реализовано 2026-08-10.** Добавлены server fallback, восстановление drafts, кеширование в IndexedDB, понятные error/completed состояния и E2E нового browser context с повторной загрузкой из кеша.

**Проблема**

Прямая ссылка `/workouts/active/:id` работает только при наличии соответствующего состояния в Zustand или IndexedDB. В новом браузере, после очистки локальных данных или на другом устройстве пользователь перенаправляется в каталог, хотя тренировка существует на сервере.

**Причина в коде**

- `frontend/src/features/workout/pages/ActiveWorkout.tsx`
- `frontend/src/api/workouts.ts`
- `backend/app/routers/workouts.py` — серверный `GET /workouts/{workout_id}` уже существует.

**Шаги реализации**

1. Добавить во frontend API функцию `fetchWorkout(workoutId)` с текущей Zod-схемой.
2. В `ActiveWorkout.boot()` сохранить приоритет восстановления:
   1. Zustand;
   2. IndexedDB;
   3. сервер по route ID.
3. При серверном восстановлении построить drafts из snapshot-плана и сохранённых подходов.
4. Сохранить восстановленную тренировку в IndexedDB и Zustand.
5. Корректно обработать `404`, завершённую тренировку и тренировку другого пользователя.
6. Для завершённой тренировки показывать summary/history, а не молча отправлять в каталог.
7. Обновить обработку Telegram `start_param`, чтобы deep link открывал серверную сессию даже без локального кеша.
8. Добавить E2E: создать тренировку API → открыть ссылку в новом browser context → увидеть активную тренировку.

**Критерии готовности**

- Активная тренировка открывается по серверному ID на новом устройстве.
- После серверной загрузки следующая перезагрузка работает из IndexedDB.
- Чужая или отсутствующая тренировка не раскрывает данные и показывает понятное сообщение.
- Offline-восстановление существующей локальной сессии не ухудшено.

## 5. P1 — основные улучшения удобства

### P1.1. Сократить страницы программ и каталога

**Статус: реализовано 2026-08-10.** Добавлены режимы «Подходят вам / Все», порции 8/20 карточек, sticky-поиск и фильтры, количество результатов, сброс, закреплённый выбор и восстановление состояния/позиции через session storage. Полные GIF в списках не загружаются.

**Проблема**

Все программы и все упражнения рендерятся одной длинной лентой. На ширине 320 px каталог достигает около 17 000 px, программы — около 5 800 px. Пользователю трудно сравнивать варианты, возвращаться к фильтрам и находить выбранные упражнения.

**Затрагиваемые файлы**

- `frontend/src/features/workout/pages/ProgramsPage.tsx`
- `frontend/src/features/workout/pages/WorkoutCatalogPage.tsx`
- `frontend/src/features/workout/components/ExerciseCard.tsx`

**Шаги реализации**

1. На странице программ первым экраном показывать 2–4 подходящих варианта.
2. Остальные программы спрятать под переключателем «Подходят вам / Все программы».
3. Закрепить поиск и активные фильтры при прокрутке.
4. Показывать количество результатов и кнопку сброса фильтров.
5. Добавить пагинацию, infinite scroll или виртуализацию каталога упражнений.
6. В каталоге добавить закреплённую панель «Выбрано N» с быстрым просмотром/удалением выбранных упражнений.
7. Сохранять поиск, фильтры и позицию прокрутки при возврате из деталей.
8. Проверить производительность анимированных GIF: не загружать полное медиа в списке.

**Критерии готовности**

- На старте отображается небольшой релевантный набор, а не вся база.
- Возврат из деталей не сбрасывает фильтры и позицию.
- В DOM одновременно нет сотни тяжёлых карточек.
- Выбранные упражнения всегда доступны без прокрутки к началу/концу страницы.

### P1.2. Сделать GIF заметным без перегрузки тренировки

**Статус: реализовано 2026-08-10, требуется device QA.** В режиме «Зал» показывается короткое медиа-превью с отдельным раскрытием полной техники; при смене упражнения панель снова сворачивается.

**Проблема**

В простом режиме GIF скрыт за кнопкой «Ещё». Пользователь может решить, что медиа отсутствует. После раскрытия полная техника заметно увеличивает высоту страницы.

**Затрагиваемые файлы**

- `frontend/src/features/workout/pages/ActiveWorkout.tsx`
- `frontend/src/features/workout/components/ExerciseMediaPlayer.tsx`
- `frontend/src/features/workout/components/ExerciseDetailModal.tsx`

**Шаги реализации**

1. Добавить рядом с названием упражнения превью 80–100 px.
2. Если GIF отсутствует, показывать нейтральный компактный placeholder, а не большой пустой блок.
3. По тапу открывать полноэкранную/нижнюю медиа-карточку с техникой и ошибками.
4. В простом режиме не выводить полный текст техники внутри основного потока подходов.
5. Сохранять `loading="lazy"`, обработку ошибок и offline fallback.
6. Проверить GIF на iOS WebKit и слабом Android-устройстве.

**Критерии готовности**

- Пользователь видит, что у упражнения есть GIF, без нажатия «Ещё».
- Подходы остаются на первом экране или близко к нему.
- Ошибка загрузки GIF не блокирует тренировку.

### P1.3. Сделать активную тренировку сфокусированным режимом

**Статус: реализовано в коде 2026-08-10, требуется device QA.** Нижняя навигация скрыта, лишний floating stop удалён, MainButton скрывается при модалках, сессия автосохраняется, а browser unload предупреждает об уходе. Safe area и Telegram MainButton нужно проверить физически.

**Проблема**

На экране одновременно доступны несколько способов завершения: кнопка в таймере, плавающий красный stop, блок завершения и Telegram MainButton. Плавающая кнопка конфликтует с нижней навигацией. Постоянное меню также провоцирует случайный уход из тренировки.

**Затрагиваемые файлы**

- `frontend/src/features/workout/pages/ActiveWorkout.tsx`
- `frontend/src/components/layout/Shell.tsx`
- `frontend/src/components/layout/BottomNavigation.tsx`

**Шаги реализации**

1. Скрывать нижнюю навигацию на `/workouts/active/:id`.
2. Оставить один заметный stop/finish-контрол и один вторичный путь через меню.
3. В Telegram учитывать MainButton и не дублировать его плавающей кнопкой без необходимости.
4. Для браузера оставить закреплённую HTML-кнопку выше safe area.
5. При попытке уйти из незавершённой тренировки объяснять, что сессия сохранена и её можно продолжить.
6. Проверить расположение на устройствах с home indicator и системной панелью Android.

**Критерии готовности**

- Ни одна кнопка не перекрывает нижнюю навигацию или поля подходов.
- На экране нет четырёх равноценных способов завершить тренировку.
- Случайный переход назад не теряет сессию.

### P1.4. Привести все зоны нажатия к мобильному минимуму

**Статус: реализовано и проверено автоматически 2026-08-10.** Кнопки и основные поля имеют минимум 44 px, мобильные ссылки расширены, значимый мелкий текст поднят до 12 px. Playwright-аудит видимых button/nav targets пройден; остаётся ручная проверка большим пальцем на 320/393 px.

**Проблема**

Многие интерактивные элементы имеют высоту 16–38 px: «Сканер», «Как вчера», фильтры, табы, «Детали», ссылки, AI-чипы и кнопки замены. Это особенно неудобно в зале и при управлении одной рукой.

**Затрагиваемые области**

- Programs, WorkoutCatalog, ActiveWorkout;
- DailyLog и BarcodeScannerModal;
- Progress, Profile, Chat;
- общие кнопки и чипы.

**Шаги реализации**

1. Распространить `tap-target`/`tap-target-x` на все интерактивные элементы.
2. Минимальный размер действия — 44×44 px, визуально маленький чип может иметь увеличенный внутренний hit area.
3. Не располагать два текстовых действия слишком близко друг к другу.
4. Проверить управление большим пальцем на ширине 320 и 393 px.
5. Добавить автоматическую проверку размеров видимых targets в Playwright.

**Критерии готовности**

- Все основные кнопки, ссылки, табы и чипы имеют hit area не меньше 44 px.
- В строках «Изменить / Удалить» нельзя случайно нажать соседнее действие.

### P1.5. Улучшить доступность

**Статус: реализовано в коде 2026-08-10.** Разрешён zoom, усилен fallback-контраст, добавлены `focus-visible`, доступные имена, минимум 12 px и единый focus trap/Escape/возврат фокуса для всех основных модалок, включая полноэкранный таймер. Axe и реальные Telegram-темы проверяются на следующем этапе.

**Проблемы**

- В `frontend/index.html` запрещён пользовательский zoom.
- Базовый `tg-hint` (`#999999`) имеет слабый контраст для мелкого текста.
- Многие подписи имеют размер 10–11 px.
- Иконки `→`, `✕`, стрелки и часть таймеров не везде имеют доступное имя.
- Не все модалки имеют `role="dialog"`, focus trap, возврат фокуса и закрытие Escape.
- Не везде определено заметное `focus-visible` состояние.

**Шаги реализации**

1. Удалить `maximum-scale=1.0, user-scalable=no`.
2. Подобрать hint/link цвета с контрастом не ниже WCAG AA для обычного текста.
3. Не использовать 10–11 px для значимой информации.
4. Добавить `aria-label` кнопкам без текстовой подписи.
5. Создать единый компонент Dialog/BottomSheet с:
   - focus trap;
   - Escape;
   - возвратом фокуса;
   - блокировкой фоновой прокрутки;
   - `aria-labelledby`/`aria-describedby`.
6. Добавить единые `focus-visible` стили.
7. Прогнать axe или аналогичную автоматическую проверку.

**Критерии готовности**

- Страница масштабируется системными жестами.
- Критичных нарушений axe нет.
- Все сценарии можно пройти клавиатурой.
- Светлая и тёмная темы проходят проверку контраста.

### P1.7. Предупреждать о несоответствии программы профилю

**Статус: реализовано 2026-08-10.** Общая функция сравнивает ограничения, место, оборудование, уровень и пол. Карточки показывают причины, выбор требует подтверждения, а главная предлагает подобрать совместимую программу. Ограничения здоровья помечаются критичными первыми.

**Проблема**

Пользователь может вручную выбрать программу другого пола, места, оборудования или уровня. Главная затем показывает её как обычную текущую программу, из-за чего карточка может противоречить данным профиля.

**Шаги реализации**

1. Создать единую функцию сравнения программы с профилем.
2. Проверять пол, место, оборудование, уровень и ограничения.
3. Не запрещать осознанный выбор, кроме действительно опасных ограничений.
4. Перед назначением несовпадающей программы показывать подтверждение.
5. На главной выводить мягкое предупреждение и действие «Подобрать подходящую».
6. Не считать пользовательский выбор ошибкой и сохранять возможность продолжить.

**Критерии готовности**

- Несовпадение видно до старта тренировки.
- Пользователь понимает, какой параметр отличается.
- Ограничения суставов имеют более высокий приоритет, чем пол/название программы.

### P1.8. Перестроить иерархию экрана питания

**Статус: реализовано 2026-08-10.** Итог и дневник вынесены вперёд, добавление открывается закреплённой кнопкой, форма сохраняет meal/граммы при закрытии, сканер и «Как вчера» получили полноценные targets, BMR/TDEE свёрнуты под пояснение.

**Проблема**

Большой блок добавления продукта находится раньше дневника и занимает почти весь первый экран. Основная информация «что уже съедено» уходит вниз. «Сканер» и «Как вчера» выглядят как маленькие ссылки.

**Затрагиваемые файлы**

- `frontend/src/features/nutrition/pages/DailyLog.tsx`
- `frontend/src/features/nutrition/components/BarcodeScannerModal.tsx`

## 6. P2 — визуальная система и полировка

### P2.1. Убрать техническую строку аккаунта со всех экранов

### P2.2. Усилить визуальную иерархию

**Статус: реализовано 2026-08-10.** Tokens и правила оформлены в `docs/DESIGN_SYSTEM.md`, добавлены surface/semantic utility-классы, нижняя навигация получила иконки и отдельный активный фон, значимый текст ограничен минимумом 12 px.

**Проблема**

Большинство поверхностей — одинаковые серые карточки с близкими радиусами и одинаковой плотностью. Главные и вторичные действия визуально конкурируют.

4. Ввести единый стиль для destructive, warning, success и disabled состояний.
5. Добавить небольшие понятные иконки нижней навигации; активность обозначать не только цветом.
6. Сократить количество текста 10–11 px и повысить читаемость hint-информации.

### P2.3. Улучшить desktop-режим

**Статус: реализовано в коде 2026-08-10.** Shell расширен до 1024 px, основные содержательные экраны ограничены 896 px, Home/Progress/программы/каталог/приёмы пищи используют двухколоночные desktop-сетки. Визуальный browser QA — следующий этап.

**Проблема**

При ширине 1440 px приложение остаётся колонкой `max-w-lg`, хотя email-вход делает браузер полноценным сценарием.

**Шаги реализации**

1. Сохранить мобильную компоновку до tablet breakpoint.
2. Для Home, Nutrition, Progress и Profile использовать ширину 720–900 px.
3. На desktop размещать summary и действия в двух колонках.
4. Не растягивать карточки программ/упражнений на всю широкую область — использовать сетку.
5. Проверить keyboard navigation и hover/focus состояния.

### P2.4. Унифицировать ошибки, загрузку и подтверждения

**Статус: реализовано 2026-08-10.** Добавлены `toUserMessage`, общий skeleton, существующий единый toast распространён на сценарии сохранения, подтверждения используют Telegram-aware `confirmAction`, модалки — общий accessibility hook.

**Проблема**

Многие страницы показывают пользователю raw `err.message`, например техническое `Request failed with status code 500`. Loading часто представлен одной строкой, что вызывает скачок компоновки. Модалки реализованы несколькими разными способами.

**Шаги реализации**

1. Добавить общий `toUserMessage(error)` с понятными RU-сообщениями для offline, 401, 403, 404, 409, 429 и 5xx.
2. Техническую причину отправлять в Sentry/лог, не показывать как основной текст.
3. Использовать skeleton только там, где он сохраняет структуру экрана.
4. Унифицировать success/error toast.
5. Перевести подтверждения и модалки на общий Dialog/BottomSheet.

### P2.5. Исправить несогласованность определения администратора

**Статус: реализовано 2026-08-10.** `AdminPage`, `MorePage` и главная используют общую `isAdminUsername`; frontend-проверка остаётся только отображением, backend продолжает быть источником авторизации.

**Проблема**

`AdminPage` читает список администраторов из `VITE_ADMIN_TELEGRAM_USERNAMES`, а `MorePage` использует жёстко заданный `filatov_slava`. Дополнительный настроенный администратор сможет открыть страницу напрямую, но не увидит пункт меню.

**Затрагиваемые файлы**

- `frontend/src/pages/AdminPage.tsx`
- `frontend/src/pages/MorePage.tsx`
- предпочтительно общий `frontend/src/utils/adminAccess.ts`.

**Шаги реализации**

1. Вынести парсинг списка администраторов в одну функцию.
2. Использовать её и для маршрута, и для пункта меню.
3. В перспективе получать роль из проверенного backend-профиля, а не считать frontend-проверку авторизацией.

### P2.6. Улучшить offline cold start

**Статус: реализовано и проверено E2E 2026-08-10.** Минимальный профиль кешируется, восстанавливается только при JWT и локальной тренировке, баннер сообщает об offline/sync, после события online профиль перепроверяется. Cold start подтверждён Playwright-сценарием.

**Проблема**

В браузере при холодном offline-старте `Shell` не может загрузить профиль и сбрасывает frontend user в `null`, хотя локальная тренировка может быть восстановлена. В результате рядом с offline-сценарием может появиться форма входа или пропасть контекст профиля.

**Затрагиваемые файлы**

- `frontend/src/components/layout/Shell.tsx`
- `frontend/src/store/userStore.ts`
- `frontend/src/db/syncQueue.ts` или отдельный profile cache.

**Шаги реализации**

1. Кешировать минимальный безопасный профиль последнего вошедшего пользователя.
2. При валидной локальной сессии и отсутствии сети восстанавливать cached user в offline-режиме.
3. Не считать cached identity повторной серверной авторизацией: запрещать сетевые/чувствительные действия до проверки JWT.
4. Показывать единый баннер «Офлайн — изменения синхронизируются позже».
5. Добавить E2E cold start: вход онлайн → кеш → новый запуск offline → продолжение локальной тренировки.
