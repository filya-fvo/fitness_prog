# Комплексный аудит Fitness Mini App

Дата: **14 сентября 2026 года**. Основание: предоставленная матрица `fitness_app_testing_prompt_and_matrix.md`, версия 1.0.

**Итог: приложение работоспособно в проверенных сценариях, но полная приёмка по матрице пока не закрыта.** Штатные тесты прошли. Дополнительные проверки выявили проблемы подбора программ, доступности, системной темы браузера и контроля качества релизов. Этот документ предназначен для планирования последующих исправлений; исправления приложения в рамках аудита не выполнялись.

## 1. Оценка для владельца

Сильная сторона продукта — уже работающие основные сценарии: дневник тренировок, расписание, восстановление сессии, питание с подтверждением OCR, замеры, разграничение FREE/PLUS, поддержка и админские операции. Есть существенный набор автоматических проверок, локальные OCR/LLM, раздельные сервисы и действующие механизмы резервного копирования.

Главный недостаток — зелёный набор тестов пока не гарантирует правильность персонального назначения. Например, мужчине-новичку, выбравшему дом и только собственный вес, автоматически назначается программа с гантелями. При выборе нескольких ограничений по суставам рекомендации могут учитывать только одно из них. Это следует исправить первым.

Второй системный недостаток — недостаточное покрытие доступности рабочих экранов. Стандартный Lighthouse оценивает справку, где результат хороший, тогда как дополнительный axe-аудит обнаружил нарушения в 30 из 43 проверенных конечных состояний интерфейса. Это число состояний, а не число уникальных страниц или дефектов.

Рекомендация: сначала закрыть D-01–D-03, затем исправить доступность и тему, после этого выполнить оставшиеся интеграционные и проверки на реальных устройствах. Оснований объявлять приложение полностью проверенным на всех платформах нет. Подтверждённых аварий уровня P0 в выполненных проверках не обнаружено; это не доказательство их отсутствия за пределами проверенного объёма.

## 6. Подтверждённые проблемы и задания на исправление

Приоритеты: **P1** — исправить до следующего расширения аудитории/значимого выпуска; **P2** — ближайший цикл исправлений; **P3** — улучшение. Метка axe `critical` относится к доступности и не означает аварию сервера уровня P0.

### D-01. Подбор не соблюдает несколько ограничений одновременно — P1

**Доказательство:** выполнение действующего `recommendPrograms` на seed-каталоге, 72 сочетания. Пример: женщина, новичок, зал, ограничения `no_knee` и `no_spine`. Результат — «Ж · Зал · Новичок · Без нагрузки на позвоночник», поддерживается только `no_spine`.

**Воспроизведение:** в анкете выбрать оба ограничения, завершить. Онбординг назначает первый результат ранжирования без дополнительного фильтра совместимости.

**Причина:** ограничения участвуют в балльной оценке. `matchesCoreProfile` не служит обязательным фильтром; функция сохраняет неподходящие кандидаты и имеет fallback на каталог. Отсутствие точной программы не блокирует автоматическое назначение.

**Исправить:** сделать весь набор ограничений обязательным условием автоматического назначения. Если кандидатов нет, сохранить анкету и показать понятное объяснение с ручным выбором/уточнением. Не менять ограничения молча.

**Критерий приёмки:** для всех 72 сочетаний либо выбрана программа, поддерживающая весь набор, либо автоматического назначения нет и показано объяснение. Добавить проверки на реальном seed и хотя бы один браузерный сценарий с двумя ограничениями.

**Места:** `frontend/src/utils/programRecommend.ts:90`, `:208`; `frontend/src/features/onboarding/pages/OnboardingPage.tsx:229`. **Ответственность:** frontend + владелец каталога. **Артефакт:** `recommendation-boundaries.json`.

### D-02. Автоматически назначается отсутствующий инвентарь — P1

**Доказательство:** P-06, P-10, P-13, P-15; UI сохраняет несовместимое назначение в обоих браузерах. Наиболее чистое воспроизведение — P-13, без адаптации исходного инвентаря.

**Воспроизведение:** новый профиль → мужчина → новичок → дом → только «Свой вес» → 3 дня → завершить анкету. Получается «М · Дом · Новичок · Гантели» с обязательным `dumbbells`.

**Влияние:** сразу после регистрации пользователь получает план, который не может выполнить с заявленным оборудованием.

**Исправить:** отделить строгую совместимость от ранжирования по цели/частоте. Проверять инвентарь до автоназначения. Отдельно решить, как учитывать гири/TRX/турник/фитбол, которых нет в анкете.

**Критерий приёмки:** назначенная программа не требует ни одного невыбранного вида оборудования, кроме собственного веса. Для P-13 — совместимый план либо явное отсутствие подходящего плана. Прогнать все 20 персон и отрицательные комбинации инвентаря.

**Места:** `frontend/src/utils/programRecommend.ts`, `frontend/src/features/onboarding/pages/OnboardingPage.tsx`. **Ответственность:** frontend + каталог. **Артефакты:** `persona-recommendations.json`, `persona-browser.json`.

### D-03. Push в production-ветку не запускает основной CI — P1

**Доказательство:** `.github/workflows/ci.yml:5` содержит только `branches: [main, master]`; фактическая production-ветка — `timeweb-production-20260825`. Событие `pull_request` присутствует, но прямой push в production-ветку само по себе им не становится.

**Влияние:** опубликованный commit может не получить автоматический набор обязательных проверок. Это дефект конфигурации контроля качества, а не доказательство отсутствия ручных проверок прошлого релиза.

**Исправить:** добавить production-ветку в push trigger и согласовать обязательные status checks с правилами ветки. Проверить, что релизная процедура использует результат именно публикуемого commit.

**Критерий приёмки:** следующий тестовый push/PR по принятому процессу запускает backend, frontend, browser, visual и Docker jobs; статусы привязаны к SHA релиза. Правила защиты GitHub в этом аудите не проверялись.

**Ответственность:** эксплуатация/CI.

### D-04. Недостаточный контраст на входе и рабочих экранах — P2

**Production-воспроизведение:** открыть вход в Chromium/WebKit. Белая надпись кнопки Telegram на `#229ed9` имеет контраст **3,01:1** при требуемом axe для этого текста **4,5:1**. Проблема сохраняется при явном включении тёмной темы.

**Шире:** axe нашёл нарушения в 30 из 43 конечных состояний локального интерфейса. Встречаются `color-contrast` в питании, замерах, прогрессе, соревнованиях, расписании, поддержке и админке. Повторы одного элемента на нескольких сценариях не считаются отдельными дефектами.

**Исправить:** скорректировать цвета текста/фона и общие theme tokens, затем проверить активные кнопки, ссылки, выбранные фильтры, подписи и состояния форм. Не ограничиваться только кнопкой Telegram.

**Критерий приёмки:** нет serious/critical нарушений контраста в воспроизводимых состояниях; обе фактические темы и мобильная/desktop ширина проверены. Отдельно визуально проверить результат, включая различимость disabled и active состояний.

**Места:** `frontend/src/components/TelegramBrowserLogin.tsx`, `frontend/src/index.css`, компоненты по CSS-локаторам из `ux-details.json`. **Ответственность:** frontend/UI.

### D-05. У элементов select админки нет доступного имени — P2

**Доказательство:** axe `select-name`, уровень `critical`: 6 фильтров в редакторе упражнений, 2 выбора при создании программы, 1 выбор раздела очистки в карточке пользователя.

### D-06. Системная тёмная тема браузера подменяется светлой темой Telegram SDK — P2

**Доказательство на production, оба браузера:** `prefers-color-scheme: dark = true`, настройка `system`, `initData` отсутствует, однако `data-theme="light"`. SDK на обычной странице сообщает `colorScheme="light"`. При явном выборе `dark` приложение действительно становится тёмным.

**Причина:** `currentWebApp()` принимает наличие SDK за применимый Telegram-контекст; `resolveTheme` отдаёт приоритет его colorScheme перед системной темой браузера.

**Исправить:** использовать Telegram theme только в подтверждённой среде Mini App; в обычном браузере при `system` учитывать `matchMedia`. Явный выбор пользователя сохранить.

**Критерий приёмки:** обычный браузер с загруженным SDK, пустым initData и тёмной системной темой открывается тёмным; настоящий Telegram следует своей теме; ручные light/dark сохраняются после reload.

**Места:** `frontend/src/theme/theme.ts:24`, `frontend/src/lib/telegram.ts`. **Артефакт:** `theme-production.json`; изображения `theme-chromium-system.png` и `theme-chromium-dark.png`.

Важно для трактовки результатов: часть первоначальных замеров с системной настройкой dark фактически показывала светлую тему. Проверка явной тёмной темы проведена отдельно; полное покрытие тёмных авторизованных экранов не заявляется.

### D-07. Часть мобильных кнопок уже минимальных 44 px — P2

**Исправить:** обеспечить минимум 44×44 для самостоятельных кнопок и проверить расстояния между ними на 320 px. Маленькие checkbox внутри кликабельного label не включать автоматически в дефект: размер полной области клика нужно оценивать отдельно.

**Критерий приёмки:** перечисленные самостоятельные кнопки имеют достаточную область нажатия, не перекрываются и не создают горизонтальную прокрутку.

**Места:** компоненты pin, порций питания, активной тренировки; общие `.tap-target`/`.tap-target-x` в `frontend/src/index.css`. **Артефакт:** `ux-details.json`, поле `mobile_small_buttons`.

### D-08. Название «Свой вес» не соответствует обязательному инвентарю части каталога — P2

## 7. Что сделано хорошо и следует сохранить

- **Восстановление тренировок и идемпотентность.** Проходят штатные сценарии восстановления активной сессии, повторной отправки и reconnect. Это важная основа для использования в зале с нестабильной связью.
- **Разделение расписания и напоминаний.** Перенос одного занятия, постоянная замена дня, отмена и подготовка упражнений до старта имеют отдельные проверяемые сценарии.
- **Тарифные ограничения проверяются на нескольких уровнях.** Есть backend-тесты прав и клиентские сценарии FREE/PLUS, включая downgrade без выхода из аккаунта.
- **OCR требует проверки пользователем.** Фото приводит к редактируемому review; автоматическое распознавание не превращается в бесконтрольную запись дневника.
- **Локальные ИИ-сервисы работают.** OCR и LLM доступны во внутренней сети. Код LLM ограничивает допустимые host и время ожидания. В контрольном ответе модель признала отсутствие данных.
- **Админские операции имеют защитные этапы.** Проверяются тест рассылки/контрольная фраза, preflight, dry-run импорта, версия программы, ограниченный экспорт и аудит.
- **Данные соревнований рассматриваются через приватность.** Тесты проверяют относительные изменения и отсутствие чужих абсолютных замеров в соответствующем ответе.
- **Адаптивная основа устойчива.** На 40 production-состояниях входа/справки и 43 дополнительных рабочих состояниях не обнаружено горизонтального переполнения; существующие визуальные эталоны проходят.
- **Production не расходится с проверяемой копией.** Commit совпадает; база доступна, очередь пуста, heartbeat свежий, backup metadata актуальны.

Эти выводы относятся к указанным доказательствам. Например, тест идемпотентности с заглушкой не заменяет проверку конкурентных транзакций PostgreSQL.

Media audit дал 110 точных GIF, 6 допустимых вариантов и 12 случаев без точного GIF. Он проверяет техническую согласованность, а не правильность техники движения во всех 128 анимациях. Генератор `audit_exercise_media.py --report` содержит старую дату и готовые фразы о визуальной проверке планки. Поэтому `media.md` используется только для таблицы технических результатов; эти исторические формулировки не считаются выполненной сегодня визуальной проверкой. Генератор стоит исправить в I-09.
