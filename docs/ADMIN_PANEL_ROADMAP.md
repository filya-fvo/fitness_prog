# План развития админки Fitness Mini App

Обновлено: 2026-08-26. Документ фиксирует последовательную доработку админки.
Каждый этап реализуется отдельно: контракт API, миграция при необходимости,
интерфейс, права доступа, тесты, документация и production-проверка.

## 1. Что уже есть

Текущая админка доступна только настроенным администраторам и содержит:

- поиск зарегистрированных пользователей;
- краткие данные аккаунта и число тренировок;
- выборочную очистку тренировок, питания и замеров;
- архивирование пользователя с двойным подтверждением;
- создание и базовое редактирование упражнений;
- создание программы и изменение её типа/уровня.

Админка пока не показывает здоровье production, историю административных действий,
подробную карточку пользователя, обращения, аналитику и ход рассылок. Редактор
программ создаёт только базовую оболочку, но не полноценное расписание.

## 2. Общие правила

- Все административные API повторно проверяют права на backend; скрытой ссылки во
  frontend недостаточно.
- Опасное действие требует понятного описания последствий и подтверждения.
- Массовое или необратимое действие требует двойного подтверждения.
- Каждое изменение данных записывается в неизменяемый журнал аудита.
- Токены, пароли, OTP, полный `DATABASE_URL` и содержимое `.env.production` не
  показываются в браузере и не попадают в журнал.
- Списки имеют серверную пагинацию, поиск, loading/empty/error/retry.
- Даты показываются в часовом поясе администратора, сервер хранит UTC.
- Интерфейс работает в Telegram и обычном браузере, в светлой и тёмной теме.
- Операции над production сначала проверяются тестами; изменения БД — только новой
  append-only миграцией.

## 3. Порядок реализации

### Этап 1. «Состояние системы»

**Статус: реализован в 0.20.26.** Экран находится по адресу `/admin/system` и
использует защищённый `GET /admin/system/status`. Данные worker/уведомлений идут
из Redis, а сведения хоста — из ограниченных read-only JSON-файлов; Docker socket
к API не подключён. При отказе DB доступ сохраняется только для numeric ID из
`ADMIN_TELEGRAM_IDS`, подтверждённого подписанным JWT. Эксплуатационные действия
намеренно оставлены для этапа 10.

Цель: понимать состояние приложения без SSH.

Показать:

- доступность API и PostgreSQL;
- доступность Redis;
- heartbeat worker и время последней фоновой задачи;
- последний результат уведомлений: обработано, отправлено, ошибок;
- дату и результат последнего backup;
- текущую версию/commit и время развёртывания;
- длину очереди фоновых задач;
- срок действия HTTPS-сертификата, если его можно получить безопасно.

Состояния: **Норма**, **Требует внимания**, **Ошибка**, **Нет данных**. Для каждого
состояния показывается простое объяснение и безопасный следующий шаг.

Первая версия содержит только чтение и кнопку повторной проверки. Перезапуск worker
и ручной backup добавляются позднее, после журнала аудита. Docker socket нельзя
монтировать в API; данные хоста передаются через ограниченный read-only status-файл
или отдельный безопасный механизм.

Критерии готовности:

- отказ DB/Redis/worker корректно отображается отдельно;
- обычный пользователь не может получить системные данные;
- статус не раскрывает секреты и внутренние строки подключения;
- есть backend-тесты каждого состояния и frontend-тест loading/error/retry.

### Этап 2. Журнал действий администратора

Создать append-only журнал:

- администратор и время;
- тип действия;
- затронутый пользователь или объект;
- результат и безопасное описание;
- обезличенные значения «до/после» для разрешённых полей;
- доставка уведомления, если она предусмотрена;
- request/correlation ID для диагностики.

Журнал фильтруется по дате, администратору, действию и результату. Его нельзя
редактировать или удалять через API админки. В журнал не записываются токены,
пароли, OTP, содержимое сообщений ИИ и полные персональные данные.

Сначала подключить уже существующие операции: очистка, архивирование, изменение
упражнений и программ. Затем журнал становится обязательной основой всех следующих
этапов.

### Этап 3. Полная карточка пользователя

При выборе пользователя показывать:

- способы входа: Telegram/email, состояние объединения аккаунтов;
- дату регистрации и последней активности;
- анкету, цель, уровень и выбранную программу;
- следующую тренировку и несколько последних тренировок;
- сводное количество записей питания и замеров;
- настройки Telegram/Web Push уведомлений;
- статус подписки;
- последние безопасные события поддержки и административные действия.

Действия:

- отправить личное служебное сообщение;
- повторно отправить `/start`/инструкцию;
- выборочно очистить раздел;
- включить или отключить уведомления по явному запросу пользователя;
- архивировать аккаунт;
- подготовить выгрузку пользовательских данных.

Данные открываются блоками, чтобы карточка не выполняла множество тяжёлых запросов
сразу. Деструктивные кнопки визуально отделяются от обычных.

### Этап 4. Центр рассылок

Возможности:

- редактор текста и предварительный вид Telegram-сообщения;
- обязательная тестовая отправка только администратору;
- выбор аудитории и отображение ожидаемого числа получателей;
- немедленная отправка или расписание;
- прогресс: ожидает, отправляется, доставлено, ошибка, пропущено;
- повтор только неуспешных отправок;
- история рассылок и возможность скопировать прошлую как черновик.

Фильтры аудитории:

- все пользователи с Telegram;
- активные за выбранный период;
- не завершившие анкету;
- не тренировавшиеся выбранное число дней;
- пользователи конкретной программы;
- тариф/статус подписки.

Обязательная защита: idempotency key, ограничение скорости Telegram, двойное
подтверждение, журнал аудита, запрет параллельного повторного запуска и безопасная
обработка `chat not found`/блокировки бота.

### Этап 5. Полноценный редактор упражнений

Добавить:

- серверный поиск, фильтры и пагинацию;
- основные и дополнительные группы мышц;
- оборудование, уровень, теги и ограничения;
- правила учёта веса: общий вес, одна гантель, каждая сторона, без веса;
- технику, подсказки и противопоказания;
- просмотр GIF/видео и thumbnail до сохранения;
- автоматическую проверку URL, MIME, размера и доступности медиа;
- состояние качества медиа и поиск возможных дубликатов;
- предварительную проверку массового импорта без записи в БД.

Удаление упражнения должно блокироваться или требовать безопасной замены, если оно
используется опубликованной программой или пользовательскими тренировками.

### Этап 6. Визуальный редактор программ

Иерархия редактора:

```text
Программа
  └─ Неделя
      └─ Тренировочный день
          └─ Упражнение
              ├─ подходы/повторения или длительность
              ├─ отдых
              ├─ режим веса
              └─ комментарий
```

Добавить изменение порядка, копирование дня/недели, поиск упражнения с медиа,
валидацию пустых дней и несовместимых параметров, предварительный просмотр глазами
пользователя. Использовать состояния **Черновик** и **Опубликовано**. Редактирование
опубликованной программы не должно неожиданно переписывать уже выполненную историю.

### Этап 7. Обращения пользователей

Хранить обращения в приложении со статусами:

- новое;
- в работе;
- ожидает ответа;
- решено;
- отклонено.

Карточка содержит текст, дату, пользователя, версию приложения, среду
Telegram/browser, внутренние заметки и историю статусов. Администратор может перейти
в карточку пользователя и отправить ответ через доступный канал. Вложения проходят
проверку MIME/размера и не открываются как исполняемые файлы.

### Этап 8. Продуктовая аналитика

Показывать агрегаты без лишних персональных данных:

- регистрации и активные пользователи за день/неделю/месяц;
- воронка: регистрация → анкета → программа → первая начатая/завершённая тренировка;
- возвращаемость через 7 и 30 дней;
- начатые и завершённые тренировки;
- использование питания, замеров и ИИ;
- популярные программы и упражнения;
- успешность уведомлений.

Для метрик фиксируются определения и часовой пояс. Тяжёлые агрегаты считаются
фоново или по заранее подготовленным сводкам, а не при каждом открытии страницы.

### Этап 9. Подписки и доступ

Реализовывать только после утверждения модели монетизации:

- статус и срок подписки;
- тестовый период или компенсационное продление;
- ручное отключение доступа;
- причина изменения и обязательная запись в аудит;
- история операций и фильтр пользователей по тарифу.

Платёжная система остаётся источником истины для платежей. Админка меняет только
разрешённое состояние доступа и не редактирует платёжные реквизиты.

### Этап 10. Безопасные эксплуатационные действия

После появления аудита и экрана состояния можно добавить:

- постановку ручного backup в очередь;
- безопасный перезапуск worker;
- повтор неудачной фоновой задачи;
- очистку только просроченных OTP и завершённых служебных задач;
- диагностику SMTP/локального Qwen/Tesseract/Telegram без раскрытия секретов и массового вызова.

Каждая операция асинхронна, имеет таймаут, статус, понятный результат и защиту от
повторного запуска.

## 4. Что намеренно не добавляем

- SQL-редактор и выполнение произвольных запросов;
- браузерный терминал VPS;
- просмотр или редактирование `.env.production`;
- отображение паролей, токенов и ключей;
- восстановление production-БД одной кнопкой;
- управление Docker volumes и `docker compose down -v`;
- массовое физическое удаление пользователей;
- прямое редактирование платежей;
- Docker socket внутри API-контейнера.

Такие функции создают несоразмерный риск потери данных или захвата сервера и должны
оставаться отдельными эксплуатационными процедурами с backup и ручной проверкой.

## 5. Рекомендуемые первые релизы

1. **Admin 1:** состояние API/DB/Redis/worker, версия и read-only диагностика.
2. **Admin 2:** журнал аудита и подключение существующих опасных операций.
3. **Admin 3:** карточка пользователя и история поддержки.
4. **Admin 4:** безопасные адресные и массовые рассылки.
5. **Admin 5:** расширенный каталог упражнений и правила учёта веса.
6. **Admin 6:** визуальный редактор программ с черновиками и публикацией.
7. **Admin 7:** обращения, аналитика и затем подписки.

Перед началом каждого релиза его объём уточняется отдельной задачей. Следующий этап
не должен механически раздувать `AdminPage.tsx`: новые разделы создаются как
отдельные routes/components/hooks/API modules.
