## Найденные дефекты

### QA-001 — P0 — Кэш тренировок может перейти между аккаунтами

Локальная БД называется глобально `fitness_offline_v1`; таблицы `workouts`, `sessions`, `syncQueue` и `workoutIdMap` не имеют составного ключа/области текущего пользователя. `readCachedWorkouts()` возвращает все записи, `findResumableSession()` выбирает последнюю незавершённую сессию без проверки `user_id`, а `logout()` удаляет только JWT. Home/Progress читают этот кэш до получения серверной истории.

Риск: после выхода и входа другим аккаунтом на общем браузере новый пользователь может увидеть прогресс или восстановить активную тренировку предыдущего пользователя; его очередь также может быть отправлена под новым JWT.

Ожидание: кэш и очередь должны быть разделены по стабильному `user_id`; при смене аккаунта чужие записи не читаются и не отправляются.

### QA-002 — P1 — Офлайн-изменения профиля никогда не синхронизируются

`ProfilePage.saveBody()` кладёт офлайн-данные в `fitness_profile_draft`, но в приложении нет чтения/отправки этого ключа. Реализовано восстановление только `fitness_onboarding_draft`. UI сразу сообщает «Профиль сохранён», хотя изменения остаются только в `localStorage` и могут быть потеряны.

Ожидание: черновик профиля должен попасть в общую очередь, автоматически отправиться после `online`/рестарта и оставаться явно помеченным до подтверждения сервера.

### QA-003 — P1 — Вход по непривязанной почте создаёт новый аккаунт

Требование описывает вход по email, предварительно привязанному в Telegram-профиле. `verify_login_code()` при отсутствии владельца `auth_email` создаёт нового browser-only пользователя и выдаёт JWT.

Риск: обход заявленного пользовательского пути, дубли аккаунтов и раздельная история Telegram/browser.

Ожидание: непривязанный email получает нейтральный отказ; новый аккаунт создаётся только отдельным явно предусмотренным сценарием регистрации.

### QA-004 — P1 — Сбой SMTP возвращается как успешная отправка OTP

OTP сохраняется и коммитится до попытки SMTP. Если доставка не удалась, production endpoint всё равно возвращает `200`, `ok=true`, `delivery=dev_log`; повторный запрос затем блокируется resend-интервалом существующей записи.

Риск: пользователь ждёт несуществующее письмо и не может сразу повторить попытку; мониторинг видит ложный успех.

Ожидание: в production неуспешная доставка возвращает `502/503`, недоставленный код инвалидируется, а повтор разрешён по контролируемой политике.

### QA-005 — P1 — Сервер не валидирует биометрию и структуру анкеты

`UserProfileUpdate` принимает произвольные `dict`. Локально воспроизведено успешное создание модели с `weight_kg=-80`, `height_cm=-175`, `age=-30`. Frontend проверяет только положительность веса/роста и наличие возраста, но не разумные верхние границы; прямой API-запрос полностью обходит UI.

Риск: некорректный BMR/TDEE, подбор опасной программы и загрязнение профиля.

Ожидание: типизированная серверная схема с диапазонами, enum для цели/уровня/активности/места, нормализацией оборудования и ограничений.

### QA-006 — P1 — Создание офлайн-тренировки не идемпотентно

Очередь хранит `clientWorkoutId`, но `createWorkout()` не отправляет его серверу как idempotency key. Флаг `flushing` действует только внутри одной вкладки. Две вкладки/устройства либо потерянный HTTP-ответ могут повторно создать одну и ту же тренировку; сервер не имеет уникального client operation id.

Ожидание: уникальный `operation_id`/`client_workout_id` с серверным upsert и атомарный lease очереди между вкладками.

### QA-007 — P1 — Возможны дубли серверных уведомлений таймера

Замена таймера выполняется цепочкой `GET ref -> abort previous -> enqueue new -> SET ref` без блокировки/атомарного скрипта. Два параллельных запроса могут оба поставить job, после чего ref укажет только на один из них; второй уже нельзя отменить через текущий ref.

Риск: дубли Telegram/Web Push при быстрых корректировках таймера или повторных запросах.

Ожидание: атомарная замена job (lock/Lua/transaction), детерминированный job id и тест конкурентного планирования.

### QA-008 — P2 — Завершение тренировки может навсегда остаться в очереди

Если сервер завершил тренировку, но клиент потерял ответ, повтор `complete_workout` получает `400 Workout already completed`. Очередь считает это ошибкой до пяти попыток и оставляет элемент навсегда, хотя желаемое состояние уже достигнуто.

Ожидание: endpoint завершения идемпотентен либо sync-клиент трактует подтверждённый `completed` как успех.

### QA-009 — P2 — Верхние границы чисел не согласованы с БД

`NutritionLogCreate.quantity_grams` и `WorkoutSetCreate.weight` имеют нижнюю, но не верхнюю границу. Локально обе схемы приняли `999999999999999999`, что превышает `NUMERIC(10,2)`/`NUMERIC(8,2)` и приведёт к ошибке БД вместо управляемого `422`.

Ожидание: серверные пределы соответствуют колонкам и разумным продуктовым ограничениям; ошибки БД не раскрываются клиенту как `500`.

### QA-010 — P2 — Рассылка уведомлений молча ограничена 5000 пользователями

`dispatch_all_users()` делает `.limit(5000)` без пагинации/курсора. После роста базы пользователи за пределами первой выборки никогда не будут обработаны этим циклом.

Ожидание: пакетная курсорная обработка всей выборки с метриками lag/error и безопасным повтором.
