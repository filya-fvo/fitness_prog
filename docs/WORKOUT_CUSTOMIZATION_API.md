# API личных изменений дня программы

W1–W4: разовое и постоянное редактирование состава и серверный формат сложных методов подключены; экран методов и выполнение добавляются следующими этапами.

`GET /workouts/customizations?program_id=<uuid>&day_index=1&scope=program_day`
возвращает `program_id`, `day_index`, `scope`, `scheduled_date`, `program_version`,
`revision`, `patch`. Для `occurrence` обязательна `scheduled_date`; для `program_day` дата не задаётся.

`PUT /workouts/customizations`: те же поля контекста плюс `base_revision`, уникальный
`operation_id` (UUID), `patch`. Первая запись использует revision 0. Ответ содержит новую revision.
`DELETE` принимает такое же тело и сбрасывает только выбранную область; revision растёт,
тело правки становится пустым. Завершённые тренировки и другая область не изменяются.

Patch: `added_exercises`, `removed_exercise_ids`, `exercise_overrides`, необязательный
`exercise_order` (полный итоговый порядок). Неуказанные параметры остаются фазовыми.
`groups` задаёт связки; `set_methods` у добавленного упражнения или override задаёт методы отдельных подходов.

Доступ проверяется по текущему JWT и правам на программу; чужой user_id не принимается.
409 означает конфликт revision/состава, 422 — недопустимую правку, 404 — недоступную программу.
Повтор той же операции с тем же телом возвращает прежний результат; повтор UUID с другим телом — 409.
Сброс сохраняет tombstone/revision и не допускает повторной записи с прежней revision 0.

Порядок построения: исходный фазовый план → постоянный patch → legacy замены на дату
→ разовый patch. Одни и те же правила используются preview/start/offline preparation.
`customization_revisions` в снимке сообщает revisions применённых областей.
Планы/шаблоны каталога не меняются; старые snapshots сохраняют свои результаты.

`GET /workouts/planned-plan?include_saved_override=false` возвращает фазовый план с постоянными личными правками, но без правок на дату. Современный occurrence PUT/DELETE атомарно заменяет старый draft replacements этой даты, поскольку полный patch включает все её изменения.

Для исходного шаблона GET planned-plan принимает одновременно `include_saved_override=false` и `include_personal_override=false`. `customization_scopes` перечисляет действующие личные области, `customization_revisions` включает и tombstones.

Современный клиент передаёт `base_program_day_revision` дополнительно к revision выбранной области. Для переноса текущей разовой подготовки в постоянный план: `scope=program_day`, `promote_date`, `base_occurrence_revision`; перенос и запись постоянного patch атомарны. Другие date drafts проверяются на совместимость; при конфликте409 обе области сохраняются.

Сохранения обоих форматов используют блокировку users, затем пользователь/программа/день. Календарные перемещения переносят только date rows, сохраняя revision/tombstones; занятая подготовленная дата не перезаписывается молча. Отменённый legacy draft освобождает свой слот только при реальном переносе в него.


## Формат выполнения 2

План с методами или связками хранит `execution_version:2`. У упражнения `set_methods`
содержит `set_number`, `kind:drop|cluster`, 2–8 `parts` с `target_reps`, необязательным
`target_weight` и `pause_after_sec`. Последняя часть имеет нулевую внутреннюю паузу:
последующий отдых выбирается движком подхода/связки. Известные веса кластера одинаковы,
дропа — положительны и строго убывают; выполненная часть требует повторов и веса.
Веса ограничены 10000 кг и двумя десятичными знаками.

Группа: UUID `id`, `kind:superset|triset|circuit`, последовательные уникальные
`exercise_ids`, `rounds`, `transition_sec`, `round_rest_sec`. Участники принадлежат
плану, не пересекаются с другими группами и имеют target_sets=rounds. Новый v2-план
содержит 1–20 упражнений, по 1–20 подходов; превышение даёт ошибку, без усечения.

`POST /workouts/{id}/sets` для v2 передаёт `execution_version:2`, `execution_kind`,
`base_execution_revision`, `client_operation_id` (UUID) и полный упорядоченный список
`parts`: UUID `id`, `ordinal`, `reps`, `weight`, `duration_sec`, `status` и `rest_after_sec`.
Статусы: pending/completed/skipped. weight_mode общий, хранится у родителя.
Родитель сложного подхода всегда имеет reps/weight=null. is_completed вычисляет сервер:
нет pending и есть хотя бы одна completed; полностью пропущенный подход не выполнен.

Ответ содержит `execution_revision` и все части. При первой offline-записи разрешены
клиентские UUID вместо ещё пустых серверных частей; после сохранения ID неизменяемы.
Чужой UUID не привязывается к другому подходу. Полный родитель, части и receipt сохраняются
одной транзакцией; подход блокируется от параллельной записи. Старый UUID операции с тем
же телом возвращает первоначальный ответ даже после новых записей, с другим телом —409.
Устаревшая revision —409, без потери обоих результатов.

v2 требует явную версию при start/set/plan/complete. Старый редактор подготовки не меняет
современную разовую подготовку. Начатый сложный план сохраняет свою структуру; изменения
методов/связок выполняются в подготовке будущей тренировки. REST и Android sync dispatch
используют один сервис и одну response-схему, включая части. Обычная v1-очередь совместима.
При старте с клиентским program snapshot сравниваются customization_revisions; старый
снимок получает409. Повтор уже созданной тренировки возвращает её исходный снимок.

Миграция `20261019000001_structured_workout_execution.sql` сохраняет старые слоты,
веса и повторы; добавляет дочерние части и receipts, не меняя уникальность родителя.
Web восстанавливает до20 новых слотов и все фактически сохранённые legacy-слоты,
включая редкие большие номера, без генерации пустых промежутков.


### Подготовка для старта без сети (web W9)

GET `/workouts/offline-context?start=YYYY-MM-DD&days=1..14&execution_version=2` выдаёт `preparation_fingerprint` для каждого варианта. Без capability2 сложный план вызывает409; обычные legacy-планы остаются совместимыми. Ответ ограничен6 MiB, при413 клиент предлагает явно меньший диапазон без усечения упражнений/частей.

POST `/workouts` может передать `preparation: {prepared_at, schedule_fingerprint, plan_fingerprint}` вместе с program_id/day_index/client_workout_id/plan/execution_version2. Под блокировкой пользователя сервер перечитывает goals, проверяет расписание, версию программы, owner, дату, фазу, readiness, содержимое и private revisions. Advisory suggested_weight/name не меняют отпечаток; 100 и100.00 равны. Изменение либо другая тренировка на эту дату даёт409 до создания/расходования разовой подготовки. Повтор уже созданного client_workout_id возвращает исходную запись до проверки изменившегося отпечатка. Старый Android stamp остаётся отдельным совместимым контрактом до этапа A2.
